# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`jobsmith` is both a **product** — a general-purpose conversational agent (`python -m jobsmith`) that answers simple messages directly and **runs** everything else on the job engine: a task runs inside the turn and answers there, and one that outlives a clock is promoted to a **background job** and surfaced back into the conversation when it lands (#83) — and the **domain-agnostic framework** it is built on (LangGraph, object-oriented node pattern): a registry-driven planner emits a DAG of pluggable capabilities (self-describing agentic sub-graphs); a wave-based executor fans them out in parallel; a generation pipeline merges their results; each run is a persistent, trackable, cancellable **Job**; a chat layer (`jobsmith/chat/`, LangGraph prebuilt ReAct agent) sits on top. **`jobsmith/agents/` holds the agent definitions** (a capability pack + a profile: `default` = grounding (`read_files`/`prior_jobs`/`documents`)→research→analysis→critique (+ `slide_deck`), `banking` = the domain example) and **`jobsmith/app/` is the composition root that runs any of them** (provider selection, persistence, `build_app(agent=...)`).

`README.md` is the human-facing counterpart of this file: product pitch, quickstart,
CLI/API surface, limits. Keep it in sync when a command or a limit changes.

## Commands

A Makefile wraps the common ones: `make help` lists them (`install`, `install-all`, `test [T=kw]`, `lint`, `fix`, `types`, `check` = lint+types+leak-gate+tests, `eval`/`eval-llm` = score the prompts on the golden set, `serve`/`chat`/`ui`/`jobs` = the global agent, `chat-banking`/`api-banking`/`demo-banking` = the example, `clean`). Raw equivalents:

```bash
uv venv --python 3.12 .venv && uv pip install -e ".[dev,api,anthropic]"  # setup
.venv/bin/python -m pytest tests/ -q                        # all tests
.venv/bin/python -m pytest tests/test_planner.py::test_cycle_rejected  # one test
.venv/bin/ruff check .                                      # lint
.venv/bin/pyright                                           # types (config: [tool.pyright])
jobsmith serve [--port 8000]                                # ★ the daemon: it owns the job engine
jobsmith chat [--session ID]                                # ★ converse (daemon if up, else embedded)
jobsmith ui [--session ID] [--theme NAME]                   # ★ the same conversation on screen (.[tui])
jobsmith run "<task>" [--wait] | jobs | job <id> | report <id> | cancel <id>
# `python -m jobsmith …` is the same entrypoint when the venv's bin isn't on PATH
jobsmith --agent banking chat | serve                       # any agent, same shell
.venv/bin/python -m jobsmith.agents.banking.demo            # scripted banking demo (fakes)
```

The REPL is a CONVERSATION by default (chat agent; complex asks → a notice saying what will run, what it will read and what it will write → the task runs in the turn and its answer is printed verbatim → or, past `$JOBSMITH_SYNC_TIMEOUT`, a promotion to the background and a synthesis + report path on a later turn); `/bg <text>` is the explicit escalation — run it in the background and do not wait. It auto-selects the provider for BOTH stacks (`--llm=anthropic|openai|fake` overrides): the job engine uses `jobsmith/clients.py` adapters, the chat agent uses LangChain models (`langchain-anthropic`/`langchain-openai`, extras `chat-anthropic`/`chat-openai`; fake mode needs neither). Job-engine LLM selection: `AnthropicLLMClient` (`claude-opus-5`) when `ANTHROPIC_API_KEY` is set, else `OpenAILLMClient` (`gpt-5.1`; honors `OPENAI_BASE_URL` for Ollama/vLLM/gateways) when `OPENAI_API_KEY` is set, else the deterministic `KeywordLLM` fake. Both real adapters live in `jobsmith/clients.py`, implement chat+vision, take an injectable `client` for tests, and raise `RuntimeError` on refusals so they flow through the framework's NodeError path. Both adapters also book each response's tokens into the usage ledger (`core/usage.py`) instead of discarding the SDK's `usage`, pricing it by the model the *response* reports (so a server-side fallback is billed as what actually served); `$JOBSMITH_PRICES` overrides the price table. Provider quirks handled there: the Anthropic adapter drops `temperature` (removed on Claude Opus 5 — sending it 400s), hoists `system` messages to the top-level param, and enables server-side refusal fallbacks; the OpenAI adapter drops `temperature` and uses `max_completion_tokens` for reasoning models (gpt-5*/o*).

### Working on this repo

- **One short-lived branch per issue**, off `main`: `feat/<n>-<slug>`, `fix/<n>-<slug>`, `chore/<slug>` (`gh issue develop <n>` creates one already linked). Open a PR, let CI run, merge, delete. **No `develop` branch**: there are no releases yet, so it would only add a merge — the PR + CI is the integration point it used to provide. Releases, when they come, are tags.
- `main` stays green. CI (`.github/workflows/ci.yml`) runs what `make check` runs — lint, **types**, the leakage gate, tests — on push and PR across Python 3.11 and 3.12, plus `uv lock --check` so the lockfile cannot silently drift from pyproject. CI installs **every** extra, so it is the stricter reading: the optional providers' imports resolve there and are type-checked, where a plain `make install` (`.[dev,api]`) leaves them unresolved.
- **The type gate (`make types`, pyright)** is the only check here that can see a bug no test can. A signature that lies is not observable at runtime — the one that prompted #31 (`compose_reporters` promising `Reporter`, returning `Reporter | MultiReporter`) was spotted by accident in VS Code and would never have failed CI. pyright rather than mypy *because* of that: they report the same findings, but Pylance **is** pyright, so `[tool.pyright]` in `pyproject.toml` is one configuration for the editor and the gate instead of a permanent split.
  - **`reportTypedDictNotRequiredAccess` is on** (#31 phase 2) — it is a *read-discipline* gate on the state schemas. `AgentState`, `CapabilityBaseState` and `CapabilityOutputState` are `total=False` because a LangGraph node returns a **partial update**; that is right for writes and wrong for reads, so the rule asks every `state["k"]` to justify itself. Its 31 hits were by key — `query` 17, `aspects` 3, `generated_query` 3, `queries` 2, `found`/`notes`/`output`/`draft_answer`/`ok`/`data` 1 each — and only **two** touched `CapabilityResult`; an earlier note here claiming they concentrated there was simply wrong. Two guarantees, one expressible in a type: `query` is guaranteed **at entry** (`runner.stream()` invokes the graph with it, and the executor's `Send(node, state)` hands each sub-graph the whole parent state) and is now `Required[str]` in `AgentState` and `CapabilityBaseState` — free, because **no node is annotated `-> AgentState`**, they all return plain `dict`. Everything else is guaranteed only **by graph order** (`draft_answer` exists when `validate_output` runs, not before), where `Required` would be a lie: those read with `.get()` plus a default that states what missing means, next to a comment naming the node or router that guarantees it. **Never blanket-`# pyright: ignore` this rule** — a site where neither is honest is a finding about the graph, not noise.
  - `reportMissingImports` is a **warning**, not an error: the optional extras are imported lazily behind `try/except ImportError`, and their absence under `.[dev,api]` is a fact about that environment, not a defect. A misspelled import stays visible and is loud at runtime anyway.
  - Scope is `jobsmith/`. `tests/` and `evals/` are out, and `typeCheckingMode` is `basic`, not `strict` — the point is a gate that holds, not a maximal one.
  - pyright is a Python wrapper around a bundled JS checker: it needs a `node` on `PATH`. GitHub runners have one; without one it silently downloads a node build on first run, which is why `make types` is fast here and may not be on a fresh machine.
- **`main` is protected**: PR required, the three checks must pass, admins included, no force-push. **Status checks are strict** — a branch must contain the current `main` before it can merge, so CI validates the *post-merge* state rather than a stale snapshot. When several PRs are in flight, each merge invalidates the rest: bring them up to date with `gh pr update-branch <n>` (or a rebase) and let CI re-run.

  This exists because green checks on a stale base do not mean the merge is green. Git only sees *textual* conflicts; two PRs can merge cleanly and still break each other — one renames what the other calls, one reshapes an output the other asserts on. Three PRs in the first parallel batch merged on stale CI and survived only because the combination was verified by hand each time.
- **`uv.lock` is committed** and must be regenerated (`uv lock`) in the same commit as any dependency change. This project has already been bitten by version drift (`create_react_agent` deprecation, the removed `llm_input_messages` channel, checkpoint-sqlite's `isolation_level`), which is exactly what the lockfile prevents across sessions.
- **Parallel sessions use git worktrees**, one per issue — separate checkouts of the same repo, so two sessions never fight over the working tree or the current branch:

  ```bash
  make worktree B=feat/1-grounding      # checkout + venv + .env, ~1s (uv cache)
  cd .claude/worktrees/feat-1-grounding
  make check                            # each worktree has its OWN .venv
  make worktree-rm B=feat/1-grounding   # after the PR is merged
  ```

  Gotchas, both verified: a venv is **path-specific** (its shebangs are absolute), so a worktree needs its own — never symlink or copy one; and `.env`, `agent.db`, `artifacts/` are gitignored, so a fresh worktree has **no API key** until it is copied (the `make worktree` target does it). `.claude/worktrees/` is gitignored, which is also where Claude Code's own `EnterWorktree` puts them.
- `make coverage` reports per-module coverage (89% overall; `jobs/` and most of `core/` at 100%). The thin areas are still the interactive layers — `cli/main.py` 51%, `cli/repl.py` 72%, `chat/tools.py` 78% — so a change landing there needs its tests written *with* it, not after. `cli/repl.py` is only that high because #50's rendering arrived with its tests; the argparse entrypoint has none of that.

Domain-leakage gate (`make leak-check`, must return nothing): `grep -ri --include="*.py" "banking\|banquier\|votre\|analyste" jobsmith/core jobsmith/jobs jobsmith/chat jobsmith/api jobsmith/app jobsmith/cli jobsmith/tui jobsmith/agents/default jobsmith/agents/base.py` — note it scans `agents/default` and `agents/base.py`, **not** `agents/banking`, which is allowed to be as domain-specific as it likes.

### The inbound port (`service.py`)

`AgentService` is **the** use-case surface of the application — sessions and jobs — and `LocalAgentService` is its in-process implementation over a composed `AgentApp`. Every entrypoint is an *adapter* over it, never a second implementation:

| adapter | backing |
|---|---|
| `cli/repl.py`, `cli/main.py` | `AgentService` (either backing) |
| `api/app.py` | `LocalAgentService` — each route is serialization + one call |
| `cli/client.py` `DaemonClient` | the same port, backed by HTTP |

**Live progress and produced files are part of the port** (#48, step 1): `subscribe`/`unsubscribe`, `list_outputs`, `find_output` are on `AgentService`, so a front-end no longer has to ask which backing it holds before it can show a DAG move. They were `LocalAgentService`-only while the HTTP adapter already republished them (`/events`, `/jobs/{id}/outputs/...`) — the missing half was a *consumer*, and a UI written against "the port, plus these four when embedded" is a UI written against two ports. `DaemonClient.subscribe` reads the SSE stream in a background task into an `asyncio.Queue` of the same event dicts, dropping on a full queue exactly as `InProcessEvents` does — a frozen consumer must not back-pressure the socket and through it the daemon's own publish. **`None` on that queue is not an event**: it means the stream is over, and it is the last thing carried (#48 step 3). A stream that ends looks exactly like a stream with nothing to say, and the stderr note the reader prints is unreachable for a front-end that owns the terminal — so the fact travels where the consumer is already waiting, and it is never dropped, the drop rule being that the next event supersedes the missed one. `find_output` says what it can honestly say: the path is on the machine that **ran** the job, so it locates a file (what a UI prints, what `/jobs/{id}/outputs/{name}` serves) and never promises the caller can open it — but the *answer* is identical on both sides, which is why the remote backing probes the download route instead of trusting the record it already holds, and a deliverable deleted since the job finished reads as `None` either way. `tests/test_service.py` drives the same sequence through both backings and asserts **identical answers**, and greps the API module for leaked use-case code (`create_job(`, `ainvoke(`, `__interrupt__`, …). Adding a UI or a bot = one adapter, zero new use cases.

**The port narrows what it can throw, and that list is the whole contract** (#64). Three exceptions are part of `AgentService`, and a front-end may plan for exactly these: `BinaryDeliverable` (the main deliverable is not text), `ChatStreamError` (a turn did not arrive whole) and `ServiceUnavailable` (**the backing could not be reached**). Each reads identically on both backings, which is what lets a UI answer them *by name* instead of wrapping every call in a broad `except` — and a broad `except` is a stance, not a fix: it swallows this project's own bugs to catch a daemon's absence. So the translation is deliberately one class wide. `DaemonClient` funnels every round trip through `_request` / `_streaming` (the only two places a request leaves the process) and translates `httpx.TransportError` — the request never reached the daemon, or the connection died before it answered — and **nothing else**: a daemon that answered 500, or with a body nobody can parse, is *there*, and that is a defect somebody should see as one. `LocalAgentService` translates nothing at all, because a process cannot lose contact with itself: a `KeyError` from a store stays a `KeyError`, and must, or a reconnect message would sit where a stack trace belongs. That asymmetry — a case one backing can reach and the other cannot — is the same one `subscribe`'s `None` marker already has, and it is a fact about a backing rather than a licence for a caller to skip the case. The one path that does *not* translate is `_read_events`: a dead daemon is already said there as the end-of-stream marker, on the queue where the listener is waiting, and raising into a task nobody awaits would say it where nobody is. Both front-ends answer it with a single named `except` — `run_repl` around the command it is dispatching (a defect still ends the loop with a traceback) and `cli/main.py`'s `run_command` for a one-shot command — and `tests/test_service.py` asks it of *every* port method, because a translation that covers nine calls and misses the tenth is exactly the crash the tenth caller gets.

**A turn can be as long as the task it runs, and that is the point** (#83). `stream` was always a flow of events; what changed is that one of those events is a task *running*, not a model writing. The port grew nothing to say it — no timeout, no mode, no second method — because the decision belongs where the tool is (`chat/tools.py`), and a front-end that renders `token` already renders everything this produces. Two things did change on the wire and both are additive: a sixth event, `job_started`, carrying what the approval card used to carry plus the job id; and the job's answer arriving as `token`s of the turn. `tests/test_service.py` drives that through both backings and asserts the same dicts, for the same reason as everything else here — a UI told a different story by a daemon is a UI written against two ports.

**A turn is a flow, and the flow is the primitive** (#50). `stream(session_id, text)` / `stream_approval(session_id, approved)` are the abstract methods; `send`/`approve` are **concrete on the port itself**, defined as `terminal_of(self.stream(...))` — drain the events, return the one terminal. A turn is therefore driven in exactly one place, and a caller that waits and a caller that renders can never be told different things about the same turn. The events are dicts (`as_event`, built from the frozen dataclasses of `chat/runner.py`) for the same reason replies are: they cross HTTP, and a front-end deserializing a dataclass would be a third implementation. **`Message.content` is the turn's transcript, not the model's last message** — the concatenation of every `Token` yielded, in order (#83). It was the model's own message for as long as the tokens came from that message too, so the two were the same string and nothing said which one the invariant rested on. A tool that writes into the turn breaks the tie: the job's answer arrives as tokens and the model's reply is "at most one short sentence", so a terminal built from the model hands a caller that *waits* an answer with the result cut out of it — `POST /sessions/{id}/messages`, the surface a web UI will use (#8). Composing from the tokens leaves no second source of truth to drift. The one fallback is a model that streamed *nothing at all*, whose last message then stands in; it can never mask a missing job answer, because that answer is a token and any turn carrying one has a non-empty transcript. **The backing-parity suite is structurally blind to this class of defect** — it compares the two backings, which are the same code, so both are wrong together and it passes; `test_a_turn_answers_the_same_whether_it_is_waited_for_or_watched` is the one that drains a turn twice, once by `stream` and once by `send`, and compares the texts.

The two terminal dicts — `{"type": "message", "content"}` and `{"type": "proposal", "query", "rationale", "sources"}` — are byte-for-byte what `send` already returned (`sources`, the files a proposed job would open, joined them with #60: what the user approves has to be what they were shown, and it is a `list` rather than a tuple precisely so both backings answer with the same JSON).

**The overflow rule is the opposite of `/events`, and that asymmetry is the design.** A dropped progress tick is invisible and harmless — the next one supersedes it — so `subscribe` sheds under back-pressure on both backings. A dropped **token** is a lie: the sentence arrives shorter than the model wrote it and nothing in the text says so. So the chat stream never drops, and it is enforced structurally rather than by policy: there is **no queue anywhere on the path** — an async generator out of the runner, a `StreamingResponse` pulled by the server, `aiter_lines` yielded straight to the caller — so a slow reader slows the turn instead of losing part of it. What structure cannot decide, a refusal does: an undecodable SSE line raises `ChatStreamError` (where `_read_events` skips one and keeps listening), and a stream that ends without a terminal raises rather than answering with the last thing seen. `subscribe` needs its queue because a job runs whether anyone watches or not; a turn has exactly one reader, and it is waiting.

### CLI + daemon (`cli/`) — where jobs actually run

The point of this layer: **a job must outlive the command that launched it**. `jobsmith serve` is a long-lived process owning the JobManager; every other command is a *client*.

- `cli/client.py` — two backings for that one port: `DaemonClient` (HTTP, `persistent=True`) and `EmbeddedClient` (`persistent=False`), the latter being *nothing but* `LocalAgentService` owning the app it composed. `open_client()` probes `GET /health` and falls back to embedded, **printing the trade-off on stderr**. `AgentClient` remains as the CLI's alias for `AgentService`.
- **All diagnostics go to stderr** (provider/persistence/daemon banners) — stdout stays pipeable (`jobsmith jobs | cut -d' ' -f1`). The REPL's streamed turn splits the same way: the answer's tokens go to stdout as they arrive, tool activity (`… sizing up a background job`) to stderr, because "what it is doing right now" is over the moment it is read. Both are flushed per write — a line still being written has no newline to trigger one, and an unflushed answer is the silence this replaced.
- **The REPL renders the flow, with no fallback branch** (#50, step 2). Both backings stream, so an "if it cannot stream, print it in one go" path would guard a case that cannot happen. The terminal event is deliberately *not* printed: the tokens already delivered it. A `ChatStreamError` mid-turn is caught, said out loud on stderr, and the loop continues — half a printed answer followed by silence is exactly the defect the no-drop rule exists to prevent, and the conversation itself lives in the checkpointer.
- **The job notice is on stdout, and `job_lines` renders it once for both shapes** (#83). It is not "what it is doing right now" — that is the stderr rule, and it applies to `… running the task`; this is the record of what the user is being handed, and the one line they may need to read again. One renderer for the notice and for the (kept) proposal, because showing a file on one and not the other is exactly the silent decision #60 and #55 are about. The last line is `stop it : /cancel <id>`: **cancellation is the undo the approval was the gate for**, and an undo nobody is told about is not one.
- **One named `except`, never a broad one** (#64): `run_repl` wraps the command it is dispatching in a single `except ServiceUnavailable`, so a daemon that died says so on stderr and the prompt comes back — the conversation lives in the checkpointer either way — while a `KeyError` from this code still ends the loop with a traceback. `run_command` does the same for a one-shot command (exit 1, no stack). That is only possible because the port narrowed the case to one exception; see `service.py`.
- `cli/main.py` — argparse; `--llm` is exported as `$JOBSMITH_LLM` so `pick_provider` sees it from both stacks. Bare `jobsmith` == `jobsmith chat`.
- Sessions are **rebuildable by id**: the API's registry is only a cache, the conversation lives in the checkpointer under `thread_id=session_id`, so `jobsmith chat --session <id>` resumes across a daemon restart (and gets the finished-job announcement). `session_factory` therefore takes an optional `session_id`.
- Embedded mode is honest about its limit: a job still *running* stops when the process exits (`recover_interrupted` settles it on the next start). What it already did is not part of that limit any more (#63): the records are the persistence's business and the default keeps them, so the embedded banner speaks only of running jobs and the persistence banner right after it says where records live (`[persistence: sqlite — jobs kept in <path>  (default; --db=memory keeps nothing)]`). `run`'s embedded note says the record is kept once the job ends.

### Agents (`agents/`) — what an agent *is*

An agent is **a capability pack + a profile (+ an optional chat persona, + whatever it needs open)**, and nothing else — `AgentDefinition` in `agents/base.py`. The runtime, job engine, chat, CLI and API are shared by all of them, so **adding an agent touches no shared code**: define the capabilities, register the definition in `agents/__init__.py`, done. `tests/test_agents.py` pins that property (it composes a third-party agent from scratch).

```python
AgentDefinition(
    open_resources=...,   # async (stack) -> anything: pools, sessions, clients
    capabilities=...,     # (AgentContext) -> list[Capability]   ctx.llm / ctx.resources
    profile=..., chat_prompt=...,
)
```

**Resources — who opens, who closes.** The agent knows *what* to open (which backend, which collection); the composition root owns the *lifetime* and the event loop. So `open_resources` is handed `build_app`'s own `AsyncExitStack` and returns whatever it built: teardown happens in reverse order on `AgentApp.aclose()`, **including when startup itself failed** (`tests/test_resources.py` pins that). `build_app(resources=...)` injects them instead (the demo and tests use it; the caller then owns them).

**Several capabilities on one backend**: share the *connection*, give each capability **its own adapter** for the port it declared — never one fat client exposing both sets of methods. Capabilities run in parallel waves, so the shared thing must be a **pool**, not a raw connection. `tests/test_resources.py` demonstrates the exact shape (two capabilities, two adapters, one pool).

- `agents/default/`: `read_files` / `documents` → `research` (decompose into aspects, lenient JSON, then structured notes **from whatever the retrieval steps found**, see #81) → `analysis` → `critique` (the findings checked against the material they came from, see #82), plus `slide_deck` when the request wants a presentation. `analysis` and `critique` subclass `SingleStepCapability` (`_step.py`): one LLM node reading the best upstream `results` entry, degrading to the bare request when the upstream failed/was skipped — `critique` overrides that first-match rule, because a step checking a claim against its source needs both.
  - **`documents` is the grounding step** — without it a job is the model talking to itself. It depends on the `DocumentSource` **port** (`sources.py`), never on what backs it: `search(query, limit) -> list[Document]`, shaped by the need so a web or vector backend is another adapter, not a rewrite. `LocalFiles` is the first adapter (term-overlap ranking over a directory — *keyword*, not semantic; no key, no network, so tests and CI can use it).
  - **`read_files` is the other grounding step, and the distinction is the point** (#60): `documents` *searches* ("what does my material say about X"), `read_files` *reads* ("give me THAT document"). A request that names a file — very often a report jobsmith itself wrote twenty minutes earlier — could not reach it before, and a ranked search over a filename answers a different question plausibly enough that nobody notices the agent reasoned from memory about a document it was handed. So it is a second **port** next to the first (`DocumentReader.read(ref) -> Document` in `sources.py`, `LocalFileReader` the first adapter), a second capability (`read_files.py`), and two steps the planner chooses between — never one step with a mode. The named path travels as an **input** (`inputs["source_files"]`, `SOURCE_FILES_INPUT_KEY` in `core/state.py`, filled by `launch_job`'s own `source_files` parameter), never as prose the engine parses back out of the query, and `requires_inputs` is what drops the step for a request that named nothing (`is_applicable` is overridden so `source_files: []` drops it too — the key being present is not naming a file). It calls **no model**: reading a file the user named is not a judgement. A refusal is **material, not silence** — one unreadable file among three does not fail the step, and the refusal goes into the generation context as well as the report, because a model told nothing about the missing file writes confidently over the hole. What a path may be is `core/paths.py` and the roots are `build_app`'s (`reports_dir`, plus the `--docs` directory the agent already exposes for searching): the deployment decides, the capability reports what the port told it.
  - **`prior_jobs` is the THIRD referent, and it is not a file at all** (#74): *"make a one-pager out of that report"* used to reach `read_files` with the path of the document the previous run wrote, so this product re-read through the filesystem a file it had written itself minutes earlier. Four things were wrong with that round trip and only the first is about elegance. **The report is a deliverable, not a trace** — per-step material is deliberately not inlined into it — so re-reading it is reading the *thinnest* representation of the run: the final prose, never `research`'s notes nor `web_search`'s passages (measured: the deliverable of a run whose deliverable was a work plan, re-read, inherits the work plan and none of the material actually gathered). **#85 made that argument stronger**: the file is now a title, the answer and one `job_reference` line, so it carries nothing `final_answer` does not — re-reading it is reading the answer through a filesystem and losing every step's material on the way. (It also removed what was a fifth argument when this was filed — the *About this job* section coming back as if it were subject matter — because that section is gone.) It **assumes a file that exists, is text and is on this machine**, which is exactly what `find_output` refuses to promise (#49), and a PDF deliverable cannot be read back at all. It needs a **path policy for a case with no path**. And since #84 a run leaves a document only because the request asked for one, so the file may never have been written: the round trip is not merely worse, it is sometimes impossible. So a job reference is a second *input* (`inputs["from_jobs"]`, `FROM_JOBS_INPUT_KEY`) and a second **port** — `PriorJobSource.load(job_id) -> PriorJob` (the answer plus the per-step material, in plan order) — never a widening of `DocumentReader`, for the reason #60 gave about `DocumentSource`: a request naming a file and a request naming a run are two questions, and one step with a mode answers neither well. ### The composition root (`app/`)

Wiring only, no content — everything here is domain-neutral:
- `providers.py`: `pick_provider` (one `--llm=` flag / key auto-detect shared by both LLM stacks), `make_llm` (job engine, `clients.py` adapters), `make_chat_model` (LangChain), `load_dotenv`, and the keyless fakes — `KeywordLLM` plans by **parsing capability names out of the rendered planner prompt** (works with any registry), `KeywordChatModel` proposes a job on analysis-ish keywords.
- `agent.py`: `await build_app(agent=..., **overrides) -> AgentApp(manager, session_factory, agent_name, resources, registry, aclose)`. **`reports_dir` is resolved once, to an absolute path, before anything uses it** (`pick_reports_dir`: argument > `$JOBSMITH_REPORTS_DIR` > `<data dir>/reports`, #63) — every path a job records is built from it, and a record that outlives the process must not carry `artifacts/…` relative to wherever it was launched: from any other directory that is a path to nothing, which is exactly what a persistent job list would put on screen. It also declares what this deployment lets a capability **read** — `AgentContext(readable_roots=(reports_dir,))` (the resolved one), the tree the product's own paths point into, so a report a job wrote is a file the next request can name (#60). It also hands down the `PriorJobSource` a capability reads an earlier RUN through (#74) — one `StoreJobRepository` built here and given to both the manager and that port, because the registry is composed before the manager exists and two repositories over one store would be two answers to "what did that job produce". It composes ONE agent definition into a running product: providers, persistence, the agent's resources, registry, graph, JobManager, chat-session factory — all on one `AsyncExitStack`. The REPL and entrypoints live in `cli/`.
- `persistence.py`: `pick_db()` (arg > `--db=` > `$JOBSMITH_DB` > `<data dir>/jobs.db`) + `open_persistence(spec, stack)` → `(checkpointer, store)`, teardown on the caller's `AsyncExitStack`.
  - **An unconfigured jobsmith keeps its jobs** (#63). The default was `memory`, so every surface built to find a job again — `jobs`, `job <id>`, `resume`, the TUI's list, the chat's announcement — was dead on arrival in the default configuration and looked broken rather than unconfigured. The default is now a SQLite file, and **SQLite is a core dependency, not an extra**: "a file when `.[sqlite]` happens to be installed, memory otherwise" would make one command behave differently on two machines, the silent difference refused everywhere else here (a capability nothing can serve stays out of the registry; a format nothing renders fails at startup). `langgraph-checkpoint-sqlite` is pure Python, so it costs no deployment constraint; `.[sqlite]` survives as an **empty** extra so existing install commands do not fail on an unknown one. `_open_sqlite` lost its `ImportError` guard with it — its absence is a broken install.
  - **Where**: `data_dir()` — `$XDG_DATA_HOME/jobsmith` when that is set to an absolute path, **on every platform** (setting it is an explicit choice, and it is the one lever that relocates everything at once, which is how the test suite is fenced off); otherwise `~/.local/share/jobsmith` (Linux & co), `~/Library/Application Support/jobsmith` (macOS), `%LOCALAPPDATA%\jobsmith` (Windows) — stdlib only, three branches are not worth `platformdirs`. Never the working directory: a job list that depends on where the command was typed is the same surprise one level up. Reports live under it too (`reports/`, see `agent.py` below). The directory is created by the one thing that writes into it first (`_open_sqlite` makes the db file's parent, the Reporters and the artifact store make theirs), never by `data_dir()` itself. A relative `$XDG_DATA_HOME` is ignored, as the spec says.
  - **`memory` stays a supported value, and must now be asked for by name.** Every test, `evals/harness.py` and the banking demo say `db="memory"` explicitly. `tests/conftest.py::sandboxed_data_dir` (session, autouse) points `$XDG_DATA_HOME` at a temp dir, clears `$JOBSMITH_DB`/`$JOBSMITH_REPORTS_DIR` (a developer's own must not become where a careless test writes), and **fails the run** if that directory exists at the end — a `build_app` that forgot `db="memory"` is caught by name instead of quietly adding jobs to the job list of whoever ran the suite. A test exercising the default on purpose points `$XDG_DATA_HOME` at its own `tmp_path`. The same fixture makes `load_dotenv` a no-op for the session (on `app/providers.py` and on every module already holding it by name): the entrypoints load `.env` with `setdefault`, so a test driving one on a machine whose `.env` names a `JOBSMITH_DB` would refill what was cleared and write outside the sandbox, unseen (`test_the_test_process_never_reads_a_dot_env`).
  - **Every process of a user shares that file by default** — which is what makes it useful and what made #10 a prerequisite: `recover_interrupted` must not declare dead a job another live process is running. That is #10's subject and lives in `jobs/`, not here.
  - **…and so every process writes to it, which SQLite only allows if each writer asks for the lock first.** Measured with five real processes on one file (`tests/test_sqlite_concurrency.py`, driving `tests/sqlite_hammer.py` straight on the LangGraph backends so no retry hides anything). Three findings, one per backend step:
    - **The store failed at once** ("database is locked", most processes, every run): each batch opens a *deferred* `BEGIN`, reads, then writes, and a read snapshot another process committed past cannot be upgraded — WAL's `SQLITE_BUSY_SNAPSHOT`, which never consults the busy timeout. The store's connection is therefore handed over wrapped in `_ImmediateBegin`, which turns the store's own `BEGIN` into `BEGIN IMMEDIATE`: the lock is taken before the first read, so a contended batch *waits* (the 5 s `connect(timeout=...)`) and reads a current snapshot. A wrapper on the connection, because the constructor argument is the one seam the store offers and "which BEGIN" is a property of the connection; nothing of LangGraph is subclassed or patched, and a private `_cursor` override would silently diverge on the next release. It depends only on the store saying `BEGIN`, which the two-process test pins. Cost, stated: the store's read batches queue behind another process's write too. **BEGIN now waits, and a statement already on aiosqlite's thread lands even if its awaiter is cancelled** — that is safe only because the store runs every batch in a background task of its own (`AsyncBatchedBaseStore`), so a cancelled `aput` stops waiting and never interrupts a batch between its BEGIN and COMMIT; `test_a_batch_cancelled_while_waiting_for_the_lock_leaves_no_transaction` pins it, and fails with "cannot start a transaction within a transaction" if a batch ever runs in the caller's task.
    - **Opening a fresh file together raced** — the store's migrations (read version, then apply, autocommitted, nothing held: "UNIQUE constraint failed: store_migrations.v", "duplicate column name") and, rarely, the WAL switch. Both go through `_while_another_process_sets_up`, a bounded retry on exactly those messages: every such failure is the other process having just done the same step, and the next attempt resumes after it. Serialising instead would need a lock `executescript` does not break (it commits any open transaction first).
    - **The saver never failed**, before or after — measured, not reasoned: its connection keeps sqlite3's implicit transactions, which open on the first INSERT, so it asks for the write lock before reading anything and the busy timeout applies. Its test stays so that remains measured.
    - `StoreJobRepository._io`'s retry (#10) covered the first finding for job records only; with the store fixed where the connection is opened it has nothing left to catch short of a writer holding the lock past the busy timeout (measured: no "locked" error in 40 instrumented runs of #10's cross-process tests with the retry off).
  - Backends: `memory`, a SQLite path (the default, or any path you name), or a Postgres DSN (`.[postgres]`, one shared `AsyncConnectionPool` for saver + store, `autocommit/prepare_threshold=0/dict_row` as those backends require). Chat sessions share the job graph's checkpointer, so conversations persist too (namespaced by `thread_id`: `session_id` vs `job_id`).

**Why `build_app` is async**: real backends must be opened in the event loop that will use them. `python -m jobsmith api` therefore serves with `await uvicorn.Server(config).serve()` inside that same loop — `uvicorn.run()` would start its own loop and strand the pool. **SQLite gotcha** (cost an hour): the *store* needs `isolation_level=None` (it drives its own `BEGIN`/`COMMIT`; under implicit transactions its first write leaves one open and the next `BEGIN` raises "cannot start a transaction within a transaction"), the *saver* keeps the default; never run a stray `PRAGMA` on those live connections (it opens a transaction and deadlocks the other connection) — WAL is set once on a throwaway connection, and the busy timeout via `connect(timeout=...)`.
- **Interrupted jobs**: `JobManager.recover_interrupted()` runs in `build_app` — RUNNING records whose owner is provably gone (on a shared store: lease expired or pid dead, see the jobs layer and #10; on memory: any with no task here) are leftovers from a dead process, marked FAILED (checkpoint retained for a future resume); a job another live process runs is left to it; QUEUED jobs stay runnable.

## Architecture

### The OO pattern

Every graph step is a class instance owning its deps and config. Node logic is **async instance methods** registered directly (`g.add_node("planner", self.planner.run)`); routers are **sync methods**; capabilities expose `.build()` returning a compiled sub-graph mounted as one parent node. `AgentBuilder` (`core/builder.py`) is the composition root and holds references to every step instance (swap one before `.build()` in tests).

### Core concepts (read these files first)

- **`core/capability.py`** — `Capability` ABC + `CapabilitySpec` (name, description, JSON-schema dicts, `requires_inputs`). Capabilities take *exactly the clients they need* in their constructors; the framework never introspects them. Terminal sub-graph nodes call `_emit_success`/`_emit_failure` so every capability reports uniformly.
- **`core/registry.py`** — `CapabilityRegistry`: single source of truth for what the agent can do. The planner prompt, executor Send targets, and builder node map all derive from it. **Frozen at `build()`** — a compiled graph's capability set is fixed; new capability ⇒ new `AgentBuilder` (compilation is milliseconds).
- **`core/state.py`** — capability results live in one `results: dict[str, CapabilityResult]` with a dict-union reducer. Fan-in safety: each capability writes only its own key; registry-unique names + no-duplicate plan steps ⇒ disjoint keys. **Determinism caveat:** consumers must iterate in *plan order*, never dict order (ContextMerger does).
- **`core/usage.py`** — token/cost accounting. `LLMClient.chat` still returns `str`: usage travels on an **ambient ledger** (a `ContextVar` the JobManager installs per run) that adapters push into with `record_usage(...)`, because what a call cost belongs to the run, not to every call site's signature. Attribution is read from LangGraph's runtime config — the root segment of `checkpoint_ns` IS the responsible parent node (`planner`, `cap_research` → `research`) — so a capability nobody wrote for this feature is still attributed, and node signatures are untouched. Failure to resolve a scope degrades to `unattributed`, never to a wrong total. `DEFAULT_PRICES` is a dated snapshot, overridable with `$JOBSMITH_PRICES` (inline JSON or a file path, longest-prefix match); an unpriced model reports tokens with `cost_usd: None` rather than an invented number. **Not covered**: the chat layer's LangChain calls (the two-stack split) — conversation tokens are not counted.
- **`core/paths.py`** — what a path is allowed to be, answered once for everything that asks. Two questions, two answers: a **name** (`safe_name` — one component chosen by a model or a user, appended to a directory *this* code picked, so it cannot climb out; `LocalArtifactStore` uses it, and a requested report filename (#55) is the same question) and a **location** (`resolve_within` — a whole path given by a model or a user, refused unless it *lands* inside one of the roots the deployment declared readable). `resolve_within` **resolves before it compares**, which is the whole of the rule: `..` collapses and every symlink is followed, so a link out of the root is refused exactly like `../../etc/passwd` — the test is where the path lands, never how it is spelled, because rejecting spellings is a blacklist and a blacklist is a race with whoever writes the next one. An **absolute** path is not refused on sight: this product *prints* paths (`jobsmith outputs`, the TUI's artifacts pane, a report path in the conversation) and the path a user pastes back is the one they were shown, so it takes the same test and is refused only if it lands outside. Which roots exist is a deployment decision (`AgentContext.readable_roots`), never a capability's.
- **`core/prior_jobs.py`** — the `PriorJobSource` port: `load(job_id)` answers with what an earlier run produced (its answer, its per-step material in plan order) and touches no filesystem. It is here rather than beside the capability that consumes it for the reason `ArtifactStore` is: the composition root supplies it, so `AgentContext` must be able to name it. Nothing here names a store, a namespace or a schema — the adapter is `jobs/prior.py`.
- **`core/profile.py`** — `AgentProfile` is the entire domain surface: prompt templates, user-facing messages, input/output validation rules (plain callables), `max_refine`. Core defaults are neutral English; the banking example overrides them (French messages live *only* in `agents/banking/profile.py`).

### Graph flow

```
validate_input → document_intent → router ─(direct | empty registry)→ direct_answer ┐
                                     └(plan)→ planner ─(nothing applicable)→ ───────┤
                              └→ executor_dispatch ⇄ {cap_<name> × registry}
                                ↓ (all done)                     ↓
                          merge_results → generation → validate_output
                                              ↑ refine ←┘ (≤ max_refine)  → post_process → END
                                                         └(could not answer)→ unanswered → END
errors: execution_error → escalate (some ok result) | user_error (none) → END
```

- **Router** (`core/router.py`) is a dedicated triage node — the planner never decides *whether* to plan. LLM picks a route from `Router.routes` (`"plan"` → planner, `"direct"` → `DirectResponder`, which renders the registry into its prompt so "what can you do?" is answerable, then joins at `validate_output`). **Fail-open**: any LLM/parse error or unknown route falls back to `"plan"`. New route = entry in `Router.routes` + node + `AgentBuilder.route_targets` entry before `.build()`.
  - **Fail-open holds only while there is something to plan with.** An **empty registry** is routed `"direct"` *structurally* — before the LLM call, so it is deterministic and free — and the fallback goes there too (#38): `"plan"` against nothing is not a wider door but a wall, the planner can only raise and the run ends in `user_error`. That is not hypothetical, it is the price of the rule below that a capability nothing can serve stays out of the registry: an agent whose capabilities are **all** conditionally registered composes an empty one legitimately.
- **Document intent** (`core/document.py`) is the second dedicated decision node, and it exists because the *request* had exactly one reader (#90). "compare X and Y, give me that as a PDF" produced markdown from `jobsmith run`, `/bg` and `POST /jobs`: the sentence was interpreted only by the chat model filling `launch_job`'s arguments, so #61's defect survived one door over from where #55 fixed it. All four doors go through the graph, so the decision belongs in it — folding it into the router's prompt is the rule this design is following, not a shortcut it may take. It answers in the three states `Job.formats` already has (names / `[]` / nothing) — its prompt offers a fourth answer, "a document, no format named", which resolves to the deployment's default *names* (`default_document_formats`, handed down by `build_app`, #96) so nothing downstream learns a fourth state — and writes **only to state**; `jobs/runner.py` translates that node's write into `FormatsChosen` and `JobManager._apply` folds it into the record, because `PostProcessor` and `Escalator` already establish that a node does not persist. Five properties hold it up. **It fills silence and never overrides**, structurally: `GraphRunner.stream` seeds `document_formats` with the job's own `formats`, and a value there returns the node before any model call — free, deterministic, and no second interpreter that can disagree with the chat model. **It cannot refuse**, which is why it is allowed to run where nobody is listening: #55 put both document refusals in `create_job` on purpose, and this node chooses from `available_formats(registry)` (handed down by `build_app`; `core/` never learns what a Reporter is) and drops anything else. **It is fail-open like the router** — bad JSON, an unknown answer, a format nothing renders, a dead provider: all of them write nothing, which since #96 means *no file*. That is the right side to fail on: a missing document is said on the record and the answer is delivered in full either way (#85), where an invented one is a file nobody asked for. **It sits BEFORE triage**, and that is the cost: one extra LLM call on every run whose caller named no format, on both routes. It buys the symmetry #84 already promises for a format that *was* named — a reader who asked for a PDF gets one whether the router sent their sentence to the planner or answered it on the spot — and this node needs only the query, so a later placement would serve one path and not the other. **It decides formats and nothing else**: `document_title` is derived mechanically from the request (#54) and a second, interpretive derivation beside it would need a rule saying which wins.
  - **A request that says nothing about a document gets none, on every door** (#96). #84 made the request decide whether a run leaves a file, but only for a request that *spoke*: `_deliverable_wanted` answered silence by the plan's shape, so every run that planned wrote the deployment's formats. That was deliberate, and the reason was #83's promoted run — its answer went to the completion notice, which the chat model synthesises, so the file was the only place its words survived. #85 removed the reason (a promoted answer comes back on the same verbatim channel, and a run with no file is delivered whatever its length), so `_deliverable_wanted` is now `bool(job.formats)`: the request decides, not the plan, the duration or the door. It is one rule in the engine rather than a default per entry point, for the reason #90 exists and #89 rejected the per-door answer — `jobsmith run`, `POST /jobs`, `/bg` and the chat are all the same `create_job`. A request still gets a file by asking, in words (the node above) or in arguments. Four consequences. **The node's silence is now a decision, so it is recorded where it is taken**: `GraphRunner` emits `FormatsChosen(None)` when `document_intent` finishes having written nothing (LangGraph publishes a node that returned `{}` as `None`), and `_apply` turns `deliverable_expected` off *only if* `job.formats is None` — the runner cannot tell silence from a caller who already spoke (the node returns without writing in both cases), the manager can, because it holds the record the graph was seeded from. The flag therefore still only goes True → False, `create_job` still leaves `None` True (the sentence may yet ask for a file), and the terminal `else` branch stays as the backstop for a graph with no document step. **`None` and `[]` end the same way and stay two facts**: `None` is what the node may still fill, `[]` is what it must never override, so `formats or []` anywhere would deafen it to every silent request — which is why the parity test asserts `null` crossing HTTP as `null`. **The three absences keep reading apart, with one precedence added**: a silent run that then FAILED carries both "not asked for" and "did not answer", and every surface (`/report`'s 404 detail, `jobsmith report`, the REPL's `/report`) says the second — "none was asked for (the answer is in `jobsmith job …`)" points at an answer that does not exist; "why it stopped" reads first, as in `job.error` (#41). The TUI's artifacts pane may say "none was asked for" there, because it is next to a status that says failed. **The notice says it before the run**: `deliverable_filenames(name, None)` stopped guessing markdown (a filename for a file nobody will write is #55's promise broken), and `writes` has a line for `None` too — "no file, unless the request asks for one" — because leaving it out now reads as a file nobody mentioned.
- **Planner** (`core/planner.py`) renders its prompt from `registry.specs()`, validates the LLM's JSON DAG: names against the registry, drops steps whose `is_applicable(state)` is false (generalizes "vision only if image" via `spec.requires_inputs`), **prunes dropped names from surviving `depends_on`**, Kahn cycle check.
  - Validation answers one of three things: a plan with steps, an **empty plan**, or an unrecoverable `NodeError` — never two at once. Empty is reachable only by every step being dropped as inapplicable (every other defect raises, and `{"steps": []}` straight from the model is still an error — indistinguishable from a truncated response). That is a fact about the request, not a broken plan, so it travels as data and **`AgentBuilder._route_after_planner` sends it to `direct_answer`**: the decision lives in the path map, never as a rescue inside the planner. Note the executor would *also* reach a terminal on an empty plan (`_all_done` is vacuously true) — but through the generator, whose prompt forbids answering outside the context it was given, so "no context" there means "I cannot answer". Which node answers is the point of the edge.
- **A refusal is not an answer, and says so as data** (#59). A generator held to "use ONLY the provided material" must sometimes reply that the material does not answer the request — and that reply used to end the run exactly like an answer: `terminal_kind == "answer"`, job DONE, a report path announced in the chat, the person who waited three minutes finding out by reading the file. The decision the model already had to make is now asked of it **structurally**: `NO_ANSWER_INSTRUCTION` (`core/profile.py`) asks for one marker line, first line only, *only* on that path; `split_declaration` (`core/generation.py`) reads it, strips it and writes `answered: bool` into the state, and `_route_validate_output` sends a declared refusal to its own terminal node — the decision lives in the path map, like the empty plan's. Four properties hold it up. **Fail-open by construction**: the marker is asked for only when the model cannot answer, so a model that never emits it produces byte-for-byte today's run. **It is a protocol, not a grep**: only the first line is inspected, and only for the token the prompt asked for — an answer that merely *reads* like a refusal (in French, say, which is how this was found) stays an answer. **A refusal is never refined**: it is settled before the draft's validity, since re-running the generator against the same context can only repeat the refusal or invent the answer the declaration exists to prevent. **The job keeps everything** — it is DONE (`DELIVERED` in `jobs/manager.py`), results, usage, annexes and deliverable intact, `job.error` untouched because nothing went wrong; `terminal_kind` carries what kind of ending it was, and both Reporters open the file with `UNANSWERED_NOTICE` while `_notice_for` gives the chat its own branch. FAILED was rejected for the reason `_write_outputs` already gives about a failed write: it misreports the work, and it would throw away the one thing such a run has to hand back — the explanation of what was missing. A sixth `JobStatus` was rejected too: every consumer would have to learn it to say one thing `terminal_kind` already says. **What #59 did not say is where the bar is**, and the model set it at "I cannot verify": #73 states it in the prompt (nothing about the subject, not unverified material) and specifies what a refusal may contain. That is a change to the threshold and to the shape, and to nothing else here — the protocol, the reading, the routing and the fail-open are as described above.
- **Executor** (`core/executor.py`) is a pass-through node + router: computes ready capabilities each wave and returns `list[Send]`; capability nodes edge back to `executor_dispatch`. This executes an arbitrary DAG without a baked-in schedule.
- **Two error channels**: `NodeError.recoverable=False` (planner/generation failures) hard-stops into `execution_error`; capability failures are recoverable — they land in `results` with `ok: False` and the run degrades gracefully.

### Critical invariant: capability output schema

Capability `build()` MUST use `self.state_graph(PrivateState)` (which sets `output_schema=CapabilityOutputState`). Without it, the sub-graph echoes its full state (including `query`) to the parent, and two capabilities finishing in the same superstep collide with `InvalidUpdateError`. Private states extend `CapabilityBaseState`.

### Jobs layer (`jobs/`)

`JobManager` holds **only the use cases** — `create_job` / `run_job` (awaitable) / `start_job` (background task) / `resume_job` (awaitable) / `start_resume` (background) / `get_job` / `list_jobs` / `cancel_job` / `recover_interrupted`. Everything else is a collaborator behind a port, so each changes for its own reason:

| collaborator | responsibility | file |
|---|---|---|
| `JobRepository` | where records live + **the store schema** | `jobs/repository.py` |
| `GraphRunner` | drives the run, translates it to domain updates | `jobs/runner.py` |
| `JobEvents` | broadcasts progress | `jobs/events.py` |
| `Reporter` | produces the deliverable | `jobs/report.py` |

Defaults wire the v1 stack, so `JobManager(graph, store)` still works; pass `repository=`/`runner=`/`events=` to swap one. `tests/test_job_seams.py` drives the whole lifecycle with **no graph and no store** — if that stops being possible, a responsibility has leaked back in.

- **Only `runner.py` knows LangGraph's stream shape** (`{node: update}`, `cap_<name>` nodes, terminal node names). It yields `PlanReady` / `StepFinished` / `NodeErrors` / `Terminal`; the manager folds those into the Job. Two ways in — `stream()` (from the query) and `resume()` (from the thread's checkpoint) — share one translation, so the manager folds a resumed run exactly like a first one. Graph nodes stay job-agnostic — `PostProcessor`/`Escalator` do NOT write to the store; new persistence goes in the manager or the repository, never in a node.
  - **The plan publishes a summary of its own.** `PlanReady` saves the plan and persists the summary, so the event stream carries "this job moved" as soon as the planner answers. Without it the first event after `running` is the first *step*, and a front-end drawing the DAG shows "no plan yet" for the whole of that step — a picture that was already stale when it was drawn.
  - **A `cap_*` update's `results` is the whole channel, not the step's own contribution.** The stream is incremental — a mounted sub-graph is published at the superstep it completes, measured, so nothing here wants `subgraphs=True` — but what it publishes is its output *state*, and `Send(node, state)` seeds it with the parent's, so `results` comes back as the union of every step so far. Which step just finished is therefore read from the **node name**, never from the payload's keys. Reading the keys re-announced every earlier step on every wave, and `_apply`'s `now_iso()` overwrote their stamps until a four-step chain claimed to have finished inside 121µs at the end of a 3½-minute run (#53) — it also re-saved every earlier result, quadratically. The property is pinned on a chain in `tests/test_jobs.py`, as **spacing** and not as "strictly increasing": the stamps are written in `results` order, so the defect produced increasing values too and passed that reading.
- **Only `repository.py` knows the schema**: `("jobs","index")/job_id` → summary; `("jobs",job_id,"meta")` → plan/errors; `("jobs",job_id,"results")/cap_name` → per-capability result. Fine-grained state stays in the checkpointer under `thread_id == job_id`. Moving job records to SQL is another implementation of this port.
- **`jobs/prior.py` is the adapter that hands a finished run's material back** (`RepositoryPriorJobs`, `PriorJobSource` over `JobRepository`, #74): it is the only place that knows a step's result is reached through the repository, that `ordered_results()` is what puts them in plan order, and that a failed step's `error` is what it has to say. Rendering is deliberately the dumb one — `default_result_markdown`, because the capability that produced a step's result may not be registered in the app reading it back.
- **Which process owns a running job is on the record, and a cancel reaches it wherever it runs** (#10, `jobs/ownership.py`). On a store several processes open — a SQLite file, Postgres, and the default once #63 lands — `_tasks` only knows *this* process's runs, so two questions had no answer: `recover_interrupted` marked FAILED every RUNNING job not in `_tasks` (a second `jobsmith chat` on the same database declared dead the jobs the first was still running), and `cancel_job` wrote a CANCELLED tombstone the owner's next step overwrote. Both are answered from the store, the one channel every backing already shares, under `("jobs", id, "control")` (only `repository.py` knows it). Decisions:
  - **A lease, written BEFORE the job says RUNNING**, renewed on a heartbeat: owner token (per manager instance, not per pid — two managers in one process are two owners, and a reused pid inherits nothing), host, pid, pid namespace, expiry. Before RUNNING because a RUNNING record with no lease is exactly what another process's startup settles, and the gap between two writes is enough (`test_the_lease_is_written_before_the_job_says_running`).
  - **"The owner is gone" has two proofs, and either suffices**: the lease expired (it stopped renewing, on any machine), or it ran on this host, in this pid namespace, and its pid no longer exists. A pid alone is meaningless across machines sharing Postgres and is reused on one machine, so it is only ever consulted as a proof of **death**, never of life — a reused pid makes a dead owner look alive, which expiry corrects a TTL later. A lease alone would make every restart after a crash wait out the TTL, and startup is the one moment recovery looks. The pid namespace is compared because two containers on one kernel can share a hostname and a SQLite volume. `recover_interrupted` settles only provably-gone owners and says both counts on stderr (settled, and left to a live owner).
  - **Timings** (`LeasePolicy`, overridable per manager, tests shrink them): heartbeat **2 s** — it is also how often the owner reads the cancel request, so it is the worst-case delay before a remote cancel lands, and two seconds is inside the time a person waits for "did that work?"; the cost is one small read + write per running job every two seconds. TTL **30 s**, fifteen missed heartbeats — generous on purpose, because the owner's loop can stall on synchronous work (a PDF rendered in-loop) and a lease that expires under a live owner is the one mistake that lets another process settle, and then resume, a job still running; it also absorbs clock skew between hosts. The canceller waits `3 × heartbeat + 1 s` for the owner to confirm.
  - **Cancellation is a request the OWNER acts on**, never a status written over its run. `cancel_job` with no task here records `("jobs", id, "control")/"cancel"` — a key only cancellers write, which is the whole point: the summary is rewritten by the owner on every step, so anything another process writes *there* is overwritten. The owner's heartbeat reads it and cancels its own task — the mechanism an in-process cancel already uses — so the job ends CANCELLED through the same `_drive` path (results kept, files collected, checkpoint retained, announced). The canceller then waits and answers with what the store says: CANCELLED once the owner has written it; still RUNNING, request recorded, if a live owner has not acted by the deadline — never a CANCELLED the run would later contradict. **Worst-case latency** = one heartbeat + the time the run takes to reach its next `await` + one canceller poll (250 ms). A cancel that arrives after the run's last update is too late and the job ends DONE — the heartbeat is stopped *synchronously* right after the stream ends, with no `await` in between, so a stop can never land on the settlement of a run that already finished, and the canceller reports DONE rather than claiming what did not happen.
  - **A stop that is not this caller's does not propagate as one**: the task that awaits the run (`launch_job`, `jobsmith run --wait`) gets the CANCELLED job back, the run's task being `uncancel()`ed — unless a local cancel landed too, which still raises.
  - **The request is cleared by `_begin_resume`** (a message to the attempt it stopped, which would otherwise stop the resumed one on its first heartbeat) and honoured by `_begin` (a process that picks up a QUEUED job at the instant another cancels it hears the request before anything runs). For QUEUED the canceller writes the request *then* the tombstone.
  - **A takeover fences before it settles** (`_take_over`): the lease is overwritten with one of ours that has already expired, so an owner that was only stalled learns at its next heartbeat that the job is no longer its (`Heartbeat.lost`) and stops *without writing* — its next persist would overwrite the settlement and a resume elsewhere would race it on one checkpoint. `BaseStore` has no compare-and-set, so an owner whose read-then-renew straddles the fence would never see it: when the proof is only an expired lease, the takeover waits one heartbeat and re-reads, and a lease renewed since is an owner alive, left alone. A missing pid is certain and skips the wait, so a crash-then-restart stays immediate. The residue — a single heartbeat's read-then-write straddling that whole wait — needs a thirty-second stall to reach at all.
  - **A process-local store coordinates nothing**: `JobRepository.shared` is False for `InMemoryStore` (only the repository knows what store it holds), and then no lease is written, no heartbeat started, no request read — tests and evals, which force memory, are exactly as fast as before, and a job with no task here gets the tombstone it always did, because on such a store there is no other process (`test_a_process_local_store_coordinates_nothing`).
  - **LangGraph's SQLite store fails concurrent writers without waiting** — found by the two-manager tests, and #63 makes it the default: each store batch opens with a *deferred* `BEGIN`, reads, then writes, and a read transaction that must upgrade after another connection committed gets "database is locked" at once, the busy timeout never consulted (WAL's snapshot rule). `StoreJobRepository._io` retries exactly that error (8 times, 20 ms doubling, ~5 s), which is safe because the failing statement is the batch's first write and every op here is an upsert, a delete or a read. It covers the job records only; the real fix (`BEGIN IMMEDIATE`) belongs to the persistence layer, not here.
  - **Tested across a real process boundary**, because in-process doubles are how this stayed invisible — a pid that is ours is always alive and a task we hold is always cancellable. `tests/test_cross_process.py` drives two managers over one SQLite file for most properties, and runs `tests/owner_process.py` as a subprocess for two: a cancel from the test process stops the subprocess's run (whose `await run_job` returns CANCELLED and exits 0) and the job then resumes here; a SIGKILLed owner is recovered at once from its missing pid, with the production 30 s TTL still valid.
- **Events are still in-process, and that is a decision** (#100). #10's control channel is per *known* job — the owner reads two keys it already knows. A cross-process event feed asks "what changed anywhere since I last looked", which `BaseStore` cannot answer without reading the whole index each tick (no ordering, no range filter across backends): O(jobs) per subscriber, forever. So it is another `JobEvents` — Postgres `LISTEN/NOTIFY`; for SQLite `PRAGMA data_version` on a dedicated read-only connection, re-reading only when it moved — and not a manager change. Everything that reads the store (the chat's notices, `jobsmith jobs`, the TUI on F5) already sees other processes' jobs.
- **Resume** (`resume_job` / `start_resume`, `POST /jobs/{id}/resume`, `jobsmith resume <id-prefix>`, `/resume` in the REPL): `runner.resume()` re-enters the thread with `None` as input, LangGraph's "carry on" — the last completed superstep is replayed from the checkpoint and only the still-pending tasks run. Finished steps are neither re-run nor re-emitted, so the manager keeps the results the repository loaded; the plan likewise comes back from the store, not the stream. Two gates, both needed: the status must be CANCELLED or FAILED (DONE is the *other* half of #5; QUEUED wants `run_job`), **and** `runner.pending(job_id)` must be non-empty. Status alone is not enough — a job that FAILED because a node raised reached `escalate`/`user_error`, so its frontier is empty and re-entering would replay one superstep and silently do nothing; ditto a job cancelled before it ever started (no checkpoint at all — `astream(None)` there raises `EmptyInputError`). Both are refused with `ValueError`, as `run_job` refuses a wrong status. A resumed attempt is driven by the same `_drive` as a first one (same persistence, events, reporting), and its usage ledger is **seeded with what earlier attempts spent**, so `Job.usage` stays the job's total cost rather than the last attempt's. `_begin_resume` clears **two** stale facts about the stopped attempt: `job.error` (its message no longer describes the job) and `job.announced` (a job picked back up is news again). The second is load-bearing now that a cancellation is announced: without it, a job announced as stopped and then resumed to DONE is filtered out of `list_finished_unannounced` and its answer never reaches the conversation that asked for it.
- What is **not** implemented: re-running a subset of the DAG of a job that already finished. That needs a way to say which results are stale and how the plan is amended — see the note on issue #5.
- **Vocabulary (was ambiguous, now fixed)**: an **artifact/output** is what the job produces FOR THE HUMAN (`Job.outputs: list[JobOutput]` — path, format, title, role `main`|`alternate`|`annex`); a capability's intermediate payload is a **result** (state channel `results`, store namespace `("jobs",id,"results")`). `Job.report_path` is a property = the main output's path. An `annex` is a **file a step produced**, and that role is now reachable: see the capability-artifacts bullet.
- **Producing the deliverable is a Reporter's job**, not the manager's (`jobs/report.py`): `build_document(job, registry)` makes a format-independent `JobDocument`, a Reporter serializes it and returns the `JobOutput`s describing what it wrote. Three ship — `MarkdownReport` (default), `HtmlReport` (`jobs/report_html.py`) and `PdfReport` (`jobs/report_pdf.py`) — sharing `FileReporter` (build the document, write one file, describe it); a subclass supplies `format`, `extension` and `render(doc)`, or **`serialize(document, path)`** when the file is bytes rather than text. That one overridable step is the whole of what a binary format changes: the naming of the file, the `build_document` call and the `role="main"` decision stay in `write`, uncopied. `make_reporter(format, registry)` selects one from `_reporter_classes()` (unknown name ⇒ `ValueError`), and `FileReporter.binary` — read by name through `is_binary_format(format)` — is how a caller holding only a finished job's declared format knows it cannot print the file.
- **One job, several deliverables**: `Reporter.write` returns `list[JobOutput]` and the manager assigns `job.outputs = list(that)`, so asking for markdown *and* HTML is a composition choice, not a protocol change. `pick_report_formats()` (argument > `$JOBSMITH_REPORT_FORMAT` > markdown) reads a **comma-separated** list. **What it answers narrowed with #96**: it used to be "which formats, when a file is written and nobody named one", and since every planned run wrote one it was in effect the format of every silent request. A silent request no longer asks the question, so it now answers only *which* file for a request that wants a document and named no format — "write me a report" read by `document_intent`, or `DEFAULT_FORMATS_ALIAS` (`"default"`) passed by a caller (the chat model's `launch_job`, `POST /jobs`). It is never a reason to write a file. `build_app` hands the same list to the node (`default_document_formats`) and to the manager (`JobManager.default_formats`, which `create_job` resolves `"default"` against, via `ensure_formats_available(..., default=)`), so the sentence and the argument cannot disagree; the alias is resolved **before** the record and before the chat's notice, so the user is shown and the record carries the names, never the alias — and with no default given it raises rather than guessing markdown. It is still composed at startup, so `pdf` without pango fails there. `JobManager.reporter` stopped being "the deployment's default Reporter" with it: every document is now one somebody asked for, so `_reporter_for` composes the job's own formats through `reporter_factory`, and a `reporter` set on the manager is only a fixed override (the tests' swap seam). A list — `JOBSMITH_REPORT_FORMAT=markdown,html`, or a request naming two — is turned into one reporter by `compose_reporters(formats, registry)`: a single name gives that Reporter unchanged (a one-format run is byte-for-byte what it was), several give a `MultiReporter` that writes each and concatenates the lists. The collision key is the **extension** (the path is `{job_id}.{extension}`): an alias of the same Reporter collapses silently (`markdown,md` is one file), two *different* Reporters claiming one extension raise at composition — they would write the same path and `Job.outputs` would list two entries for one file. An unknown name anywhere still raises. **Exactly one output is `role="main"`** — the FIRST format asked for, since `Job.report_path`, `jobsmith report` and `/report` (whose content type follows that output's `format`) all read it; the rest are `role="alternate"`, the same document rendered again. Deliberately *not* `annex`, which stays what it says it is: per-step material a capability produced. No CLI/API flag yet, deliberately.
- **A failed write does not fail the job**: the graph answered and that answer is persisted, so a job whose deliverable could not be written stays DONE with `job.error` naming the format and the cause (FAILED would misreport the work, and is a dead end anyway — the checkpoint has nothing pending, so `resume_job` refuses it). `JobManager._write_outputs` wraps the write in its *own* `try` — widening the run's, whose `except` sets FAILED, would conflate "the graph blew up" with "the disk was full" — and the final `_persist_summary` therefore always runs; before that, an escaping exception left the store holding the RUNNING row the last finished step wrote. `ReportWriteError` (`jobs/report.py`) carries the outputs already on disk and `MultiReporter` raises it, so markdown written before HTML failed is still recorded — a file with no `JobOutput` is a deliverable nobody can find.
- **A capability can produce a file, and the job records it** (#35, step 1): `ArtifactStore` (`core/artifacts.py`) is the port — `async write(job_id, name, data) -> path` — and `LocalArtifactStore` the first adapter (`<reports_dir>/<job_id>/<name>`, composed in `build_app` and handed to the pack as `AgentContext.artifacts`). A capability takes it in its constructor like any other client, writes with `state.get("job_id", "")` (declared on `CapabilityBaseState`, NOT Required — a graph driven outside a job has none) plus a *filename*, and declares the result: `meta=artifact_meta(ArtifactRef(path, title=...))` — the `meta["artifacts"]` key `core/state.py` always documented. `JobManager._capability_outputs` reads the declarations back **in plan order** (`Job.ordered_results()`, since `results` arrives in wave order) and appends them to `job.outputs` as `role="annex", produced_by=<step>`. Four decisions worth keeping: **a port, not raw I/O** — where bytes go is a deployment decision, and a capability that calls `Path.write_bytes` can never be pointed at object storage nor faked in a test (same argument as `DocumentSource`); **a missing file is dropped and named in `job.error`** — recording it would repeat #28 (a deliverable nobody can open), staying silent would hide a capability defect behind a perfect-looking run, and the job stays DONE because the answer is the work; **annexes come after the deliverables and are never `main`**, so #28's one-main invariant and `report_path` are untouched, and they are collected even when the report write failed (the file is on disk either way); **one path is recorded once** (first declarer in plan order wins), because two `JobOutput`s for one file is the ambiguity `compose_reporters` already refuses. `with_annexes` is deliberately NOT extended to list produced files: a capability that wrote one already presents it through `render_report` — "a link to a file it produced" is what that docstring says — and the framework must not learn payload shapes.
- **A file outlives the run that produced it** (#41): `_emit_failure` takes the same `meta` as `_emit_success` (a step that wrote a chart and *then* broke must be able to say so), and `_collect_artifacts` runs at **every** terminal `_drive` reaches — cancelled, the run raised, and the normal end whether it answered or not — not only for DONE. Same reasoning as usage booked for a failed step and `ReportWriteError` carrying what already reached disk: a file recorded nowhere is "a deliverable nobody can find" (#28). Four things hold it together. **The Reporter and the collection are separate steps**: `_write_outputs` (deliverables + annexes, DONE only) calls `_collect_artifacts` (annexes alone), never the reverse — there is no report to write for a run that never answered, and a status check smuggled into the report write would say otherwise. **A job that did not answer has no `main`**, so `Job.report_path` stays `None` and `/report` still 404s: the files are offered as what they are, not as a partial success. **`job.outputs` is assigned, never appended** — a cancelled job collects, and on resume the repository hands the earlier attempt's results back, so the second collection re-derives the same list instead of doubling it. **A declared-but-absent file lands in `job.error` whatever the terminal**: a declaration only exists on a step that FINISHED (`_apply` writes `results` on `StepFinished` alone), so a ref with no file is a capability that promised what it did not leave — a defect the run stopping *afterwards* cannot explain away. It is appended after any failure reason, so "why the run stopped" still reads first, and a run someone is already inspecting is the last place to hide a second bug. The fourth terminal, `recover_interrupted`, deliberately does **not** collect: it works from index summaries (no plan, no results — collecting would mean re-loading every stale record at startup), and it is the one FAILED that keeps a live frontier, so the resume that follows collects through `_drive`.
- **The request decides what the document is called, titled and written as** (#55). `Job` carries `document_name` / `document_title` / `formats` next to `query` and `inputs` — facts about the job, recorded once, never re-derived at write time — and all three are independent: a name is not a title and neither is a format, so asking for one never silently answers the others. `FileReporter.path_for` takes the name and puts a named deliverable in **the job's own folder** (`<reports_dir>/<job_id>/<name>.<ext>`, where its annexes already are): a job id is unique and says nothing, a name says everything and is unique to nobody, and a second job called `rapport` overwriting the first is #28's "a deliverable nobody can find" from the other end. An unnamed job writes exactly where it always did. Per-job formats compose through `JobManager.reporter_factory` — a factory, not a second reporter, because what the composition root knows (the registry, `with_annexes`) has to reach a reporter built later. **Both refusals happen in `create_job`**, the last point at which whoever asked is still listening: a name that is not one path component (`document_stem` → `core/paths.py`, the same `safe_name` #60 answered the reading side with) and a format nothing can render here (`ensure_formats_available`, which composes and throws away — `.[pdf]` needs pango/cairo where the daemon runs). Refusing at the write instead would refuse three minutes and a full ledger later. The chat proposes all three and shows them before the run starts — on the `job_started` notice since #83, on the approval card where that gate was kept (`chat/tools.py`) — because a name the user never saw is exactly the second silent decision this fixes; `AgentService.launch_job` takes the same three, and the 400 the API answers maps back to the same `ValueError` on the remote backing.
- **A title is never cut mid-word** (#54): `document_title` (`jobs/report.py`) derives it from the request — whitespace collapsed so a multi-line request cannot break the markdown heading in two, cut at the last word boundary that fits and marked with an ellipsis, `DEFAULT_TITLE` when the request says nothing usable. It was `job.query[:80]`, a raw slice landing wherever the count landed (`…adaptées à un utilisate`) in the one line a reader sees before deciding whether to read the rest. One place decides it and `JobDocument.title` feeds all three Reporters; the day a job carries a title of its own (#55), this stays as the floor under it.
- **The report is a deliverable, not a trace**, and since #85 that is true of the *record* as well as of the step material: title + answer, then one line naming the run (`job_reference`). Everything else a document used to recite about itself — the request quoted in full, both timestamps, the session, the token bill, the plan table with its per-step cost column, the DAG — is **recorded, not recited**: `GET /jobs/{id}` and `jobsmith job <id>` serve it whole, and a reader who opened a file to read an answer was being handed the product talking about itself. Four decisions. **The way back stays, on every document and behind no flag** — a file nobody can trace to its run is the same class of defect as a deliverable nobody can find (#28), and it is the one thing the file cannot get from anywhere else. **`with_provenance` is the archive switch**, the same shape `with_annexes` already is (`FileReporter`, `make_reporter`, `compose_reporters`, and `build_document` sets `JobDocument.provenance` from it) and independent of it, because one is what the steps produced and the other is what the run was; neither is set in production wiring, both are there for a self-contained file. **The data is built either way and the flag only decides the rendering** — unlike `with_annexes`, which gates the *building* because that costs a `render_report` call into every capability that ran. **Nothing about the Reporters' architecture moved**: one `JobDocument`, three serializers, the PDF still the HTML page printed.
  - **The evals contract changed with it, deliberately** — see the `evals/` section: `report_provenance` now scores the job id alone and `report_covers_plan` is gone, because the property it measured is no longer one the deliverable has.
- **The HTML report takes no dependency and makes no request** (`jobs/report_html.py`): inline CSS (light/dark), and since a browser renders neither mermaid nor a fenced block, the same DAG edges are drawn as an inline SVG (`dag_svg`, longest-path columns left-to-right — the plan's step order is not assumed topological). The answer and the annexes are markdown by contract, so a deliberately small subset renderer (`markdown_to_html`: headings, lists, fences, rules, emphasis) converts them — **everything is `html.escape`d first and only our own tags are added afterwards**, which is why model output cannot open a tag; links are not rendered on purpose (an anchor means sanitizing `javascript:` URLs). Grow that renderer no further: if a report needs tables or links, take a dependency then.
  - **A list it claims to support, it must not silently reshape** (#76). `line.strip()` ran *before* the bullet match, so indentation was gone by the time an item was recognised and every level collapsed into one flat `<ul>` — measured on a real deliverable, 27 indented lines at one rank, the line introducing a group rendered as its sibling. That is not "tables or links": the renderer already claims lists, and flattening one changes what the document *says* while looking like a document. It is also why the fix is one fix — `PdfReport` prints the same page (#34), so HTML and PDF were wrong together and are right together. Three decisions. **The indentation rule is written down, not inferred per document** (`_list_level`): one level every two spaces, a tab advancing to the next level boundary (so a leading tab is one level, exactly as two spaces are), anything in between rounding down — a model that indents by three is nesting, not un-nesting. Inferring the unit from the first nested item instead would teach the renderer a unit the rest of the document does not use. **The depth comes from the stack of open lists, never from the document**: `add_item` clamps to `min(level, len(stack))`, so a jump from level 0 to level 3 opens exactly one level and no indentation a model can write leaves a tag unbalanced — the renderer's whole safety argument is that only our own tags are ever added, and an unbalanced one is that argument failing. **A nested list is opened *inside* the item above it**, by taking that item's `</li>` back (`open_list`), rather than started beside it as a `<ul>` no `<li>` contains; a flat list therefore renders byte for byte as it did, which is what `test_a_flat_list_is_unchanged` pins. Escaping is untouched — content escaped first, our own tags after — and the nested case is asserted on that too, because nesting adds tags of ours and must add none of the model's.
- **The PDF is the HTML page printed, not a post-processor over its file** (`jobs/report_pdf.py`, #34): `HtmlReport.render` is a pure function of the `JobDocument`, so `PdfReport` subclasses it, renders the same page in memory and hands the *string* to WeasyPrint — no Reporter depends on another having run, and no third layout exists. It adds two stylesheets and nothing else: `PAGED_STYLE` (`extra_style`, appended to `STYLE` — a page does not scroll, and `<details>` has no reader to open it on paper) and `DAG_STYLE` (`dag_style`, carried *inside* the `<svg>` by `dag_svg(doc, style=...)`, because a print engine applies the document's CSS to HTML boxes only and the plan would otherwise be a row of black blocks). Both seams default to empty, so the HTML deliverable is unchanged to the byte. **The engine is probed when the Reporter is constructed** (`_engine()` in `__init__`, called from `compose_reporters`), the same rule the registry applies to a capability nothing can serve: a format nothing can render fails at startup, not at the end of the first job that asked for one — and the two ways it can be unavailable get different messages, since `pip install` fixes the missing distribution and cannot fix missing pango. **This is the project's first deployment constraint**: every other extra is pure Python, `.[pdf]` needs pango/cairo *where the daemon runs*. `ubuntu-latest` has them (CI renders a PDF with no apt step — measured, not assumed); a slim container does not.
- **Capabilities present their own results**: `Capability.render_report(result)` (twin of `render_context`, which targets the model) with `default_result_markdown` as the base implementation — prose stays prose, list[str] becomes bullets, only structured values fall back to JSON. Never grow that default to learn payload shapes: override `render_report` in the capability instead.
- **What a job cost is part of its record**: `Job.usage` is the run's aggregate (`core/usage.py`), refreshed on *every* summary persist — so a job still running already shows its spend, and `/events` carries it live. The per-step breakdown lives where the step's own material does, in `CapabilityResult.meta["usage"]` (stamped by `Capability._emit_success`/`_emit_failure`, including on failure — a step that burned 40k tokens and failed is exactly the one worth seeing). `jobsmith job <id>` and `GET /jobs/{id}` show both; the deliverable shows neither since #85, unless `with_provenance` asks it to recite the record.
- `Job` also carries `session_id` (chat session that launched it) and an `announced` flag (`list_finished_unannounced`/`mark_announced` drive chat notifications).

### Chat layer (`chat/`)

`ChatSession(manager, model, *, session_id, system_prompt, checkpointer).build()` → a `langchain.agents.create_agent` (LangChain model, NOT the framework's LLMClient — deliberate two-stack split: LangChain handles per-provider tool formats; the job engine stays dependency-light).

- **`chat/runner.py` is the twin of `jobs/runner.py`** (#50), and exists for the same rule: it is the ONLY module that knows what LangGraph's `astream` emits for a chat agent — the `("messages", (chunk, metadata))` pairs, the `("updates", {node: update})` ones, the `("custom", payload)` ones, the `model`/`tools` node names, `__interrupt__`. Without it that shape leaks through the service, through the API, and into every UI. Six frozen dataclasses come out: `Token(text)`, `ToolStarted(name)`/`ToolFinished(name)`, `JobStarted(job_id, query, rationale, sources, document_*, formats)`, and the two terminals `Message(content)`/`Proposal(query, rationale, sources)` — the duality `_reply` already carried, moved from a return value to the end of a flow. All three stream modes are needed and none is redundant: `messages` carries the answer as it is written, `updates` carries what a token cannot show (which tool was called, that the run stopped on an interrupt), and `custom` carries what a **tool** has to say while it is running. **Exactly one terminal is always yielded, last**, so a caller draining it for a reply never has to interpret an exhausted stream — `JobStarted` is deliberately not one: a turn that starts a job carries on.
  - **The job's answer is a `Token`, and that is a decision** (#83). It could have been an event of its own; it is not, because a front-end already renders tokens as *the turn's answer* and this **is** the turn's answer. `_from_custom` is the only place that channel is read, so the tool and the front-ends stay strangers, and an unknown payload there is dropped rather than guessed at — an event nobody can name must never be rendered as an answer.
  - `ToolStarted` carries the tool's **real name** (`launch_job`), never a phrase. Turning it into prose a human reads is the presentation layer's business (`TOOL_ACTIVITY` in `cli/repl.py`), for the same reason `REPORT_MEDIA_TYPES` lives in `api/app.py` and not in `jobs/report.py`: the CLI and a future TUI word it differently, and neither wording belongs in the thing that reports the fact.
  - **`awrap_model_call` still injects on a streamed turn** — probed before anything was built, because it is how a finished job reaches the conversation and a streaming path that skipped it would lose that silently (the turn still answers, it just never mentions the job). It holds because the tokens do not travel *through* the middleware: LangGraph's `messages` mode taps the model's own streaming callbacks, so `handler(request)` is untouched and the notices ride on `request.override(...)` exactly as before. `tests/test_chat_stream.py` pins it through `LocalAgentService.stream`, so a streaming path that built itself a middleware-less agent fails there and nowhere else.

- **Tools** (`chat/tools.py`) wrap JobManager use-cases, scoped to the session's own jobs. `launch_job` **runs the task**: `create_job(session_id=...)` + `start_job`, then it *waits* on that task for `pick_sync_timeout()`.
- **Synchronous by default, background by promotion — decided by the clock, never by a prediction** (#83). `JobManager.run_job` (awaitable) and `start_job` (detached) were both there from the beginning and only the second was ever exposed, so the engine was reachable only by handing the user a y/N card and telling them to come back later. Four decisions hold the fix up.
  - **Always `start_job`, then wait.** Promotion is *stop waiting*: nothing is cancelled, nothing is restarted, and a promoted run is byte-for-byte the run that was about to finish. It also means a turn that dies — a TUI worker cancelled, a client hanging up, a REPL interrupted — loses the waiting and not the run, which `await run_job()` could not have promised. `asyncio.wait({task}, timeout=…)` and not `wait_for`, because `wait_for` cancels what it was waiting on, which is the one thing that must not happen here.
  - **No classification.** The obvious design is to ask the model "does this look complex?" and route on the answer. It is wrong: the cost is set by the **plan**, which does not exist when that decision would be taken, so the model is guessing a duration from a sentence and is wrong in both directions. The clock observes instead. Plan shape was considered as a second, earlier trigger (the planner answers before any step costs anything) and left out: it would need a second waiting mechanism to learn a fact the first one already reveals, and a big plan is slow anyway.
  - **The threshold is a deployment choice with an opinionated default**: `pick_sync_timeout` / `$JOBSMITH_SYNC_TIMEOUT`, 20 seconds, in the style of `pick_db` and `pick_search_depth`. Twenty because it is a *human patience* budget and nothing else — below it a person waits at a prompt the way they wait for a slow command, past it a silent conversation reads as hung. `0` is a supported value meaning "never wait", which is exactly the old behaviour. A value that is not a number is said on stderr rather than silently ignored.
  - **A promoted run ends the turn saying so**, and the completion notice (`JobNotificationMiddleware`) is what brings the answer back. A run that finished *inside* the turn is `mark_announced`ed by the tool — otherwise the middleware injects it into the very next model call of the same turn, telling the model to summarize the answer the tool result just told it not to touch. That is the paraphrase this change exists to prevent, arriving through the other door.
- **The answer is written into the turn, not returned through the model** (#83). A tool result is read by the model, which then writes the user's reply from it — so a 2 000-word answer handed back that way is an answer the model paraphrases or truncates. So it is not handed back: `final_answer` is written verbatim onto the custom channel as `Token`s, and the tool *result* says it has already been delivered and asks for one short sentence at most. The consequence is deliberate and worth stating: the model never sees the answer, so it cannot field a follow-up about its content from the thread — the job id and the file are what it has, which is #74's subject and not this one's. Where the answer should *live* — the conversation or the file — is #85, answered in the bullet below.
- **A promoted run gets the same verbatim channel, and length is what decides where the answer is read** (#85). #83 gave the *synchronous* path a channel that nothing rewrites; a run that outlived the wait still handed its answer to the completion notice, which is an instruction to the chat model, which synthesises it — so for the promoted minority the file was the only place the words survived, which is precisely why the rest of #84 could not proceed (#96 then took it: see the `document_intent` sub-bullet). `JobNotificationMiddleware._deliver` writes it onto the **same** custom channel `launch_job` uses, so the reader sees a `Token` either way and the tool and the middleware stay strangers to the front-ends. Four decisions. **The threshold is length, not duration, and it is a deployment choice with an opinionated default**: `pick_inline_answer_max` / `$JOBSMITH_INLINE_ANSWER_MAX`, 2 000 characters (~300 words), in the style of `pick_sync_timeout` and `pick_db`. Two thousand because it is a **reading** budget and nothing else — roughly a screenful and a half of terminal, what a person reads where they are standing before they would rather open a document and keep it; a transcript is a place you scroll and a file is a place you keep. Deliberately not tuned to cost or elapsed time: a four-minute run can answer in two sentences. Unlike #83's duration it is known exactly at the moment the choice is taken, which is why this one needs no clock. `0` is supported and means "never", i.e. the behaviour this replaced. **Length only decides when there is something to decide between** — a run that wrote no file has nowhere else to put its text, so it is delivered whatever its length, including at `0`: that is a rule about losing text, not a policy about length, and it is what makes #84's remaining half safe to take. **The notice's wording is `chat/tools.py::_delivered`'s**, because a reader cannot tell whether a task ran in the turn or came back from the background and being told the same thing in two registers is how they would find out for no reason; `_notice_for` takes `delivered` and it changes exactly one thing — whether the model is asked to relay the answer or told to keep its hands off it. **The write happens before the model call it rides with**, so the answer arrives and then the sentence about it; a model call that then fails leaves the job unannounced and the answer shown, which is the same trade the notice already makes and the harmless half of it.
- **The approval card became a notice, and the mechanism stayed** (#83). Nothing `interrupt()`s on the nominal path: the agent says what it is doing instead of asking whether it may. Three guarantees hung on that card and every one survives as **visibility**, on the `job_started` notice emitted before the run starts — the reformulated query (the engine never sees the thread, so a reader is what catches a referent that has gone), the files it may open (#60), and what the document will be called, titled and written as (#55) — plus the `job_id` the card could not carry, because **cancellation is the undo the approval was the gate for** and an undo whose target has no name is not one. The gate itself is kept and reachable (`pick_approval_required` / `$JOBSMITH_APPROVE_JOBS`): the port keeps `stream_approval`, the API keeps its route, `Proposal` stays a terminal, both front-ends keep the card, and the tests that drive them are kept green on that flag. It is the v1 of what a capability that spends money or does something irreversible will want, and rebuilding an approval round trip through a port, an HTTP route and three front-ends is the expensive half.
- **The job engine never sees the thread**, so "analyse that" would reach the planner with its referent gone — a silent failure (the report looks fine, it answers a slightly different question). Two guards: the tool docstring *is* the model's instruction and demands a self-contained `query` (that wording is also what the user approves), and `recent_conversation()` attaches a bounded excerpt of the last turns as `inputs[CONVERSATION_INPUT_KEY]` (`core/state.py`, key `"conversation"`) as the safety net. Bounds live in `chat/tools.py` (`MAX_CONTEXT_TURNS`/`MAX_TURN_CHARS`/`MAX_CONTEXT_CHARS`) — this rides on every launch; only human/assistant prose travels (tool calls, tool results and the `[job update]`/`[job progress]` notices are dropped). `Planner.user_message` renders it as clearly-labelled background above the request; the request stays authoritative.
- **A file the request names is shown like the query is** (#60, and #83 for where it is shown): `launch_job` takes `source_files`, the docstring tells the model to pass the path exactly as it was given and never to paste a file's contents into `query`, and the list rides out to every front-end on the `job_started` notice — and on the interrupt payload as `sources`, through `Proposal`, wherever the gate was kept (the REPL prints a `reads` line, the TUI card a `reads` row, in both shapes). A path the user never saw would be a second silent decision — the thing #55 is about — and this is the user *handing something over*, not the model restating what they asked. Empty means the key is left out of `inputs` entirely, so the planner drops the step rather than planning one that can only report that nothing was given.
- **A job the request builds on is referenced, not re-read** (#74): `launch_job` also takes `from_jobs`, and the docstring tells the model to prefer it over `source_files` every time the material came from a job of this conversation — the report that job wrote is thinner than what it produced, may be binary, and since #84 may not exist. **This is where the scope lives**: each reference is resolved through `_find` against *this session's* jobs, so `inputs["from_jobs"]` carries full ids the engine can trust and a reference matching nothing is refused before anything runs (the model can fix it in the turn, exactly as it fixes an impossible format). A job reference must not become a way to read another conversation's work, and the port cannot enforce that: it is composed once per app and an id arrives with no asker attached, which is the same reason the excerpt of the thread has to travel as an input. **What the notice does NOT yet carry is the reference itself**: `job_started` names the files a run may open (#60) and not the jobs it builds on, because the payload, `JobStarted` and both front-ends would each have to learn the field. That is a gap and not a decision against showing it — the mitigating fact is only that a referenced job was announced in this same conversation, where a handed-over file never was.
- **Notifications**: `JobNotificationMiddleware.awrap_model_call` injects two kinds of transient `SystemMessage` into the model *request* — never into state, which is what keeps them out of the persisted thread (`create_agent`'s state has only `messages`/`jump_to`/`structured_response`, and the old `llm_input_messages` ephemeral channel no longer exists).
  - **Completion** ("background jobs finished" marker): final answer + report path for unannounced session jobs, marked announced *after* the model call succeeds. First of the notices — it is an instruction to act on now. A DONE job can have **no** main output (the run answered, the write failed), so `_notice_for` states the path when there is one and `job.error` when there is not, plus any file written before the failure — never `Report file: None`; the answer is announced either way, which is the point of staying DONE. A job that did **not** answer is announced with its error *and* the files its steps left behind (#41), labelled as partial material rather than a report: holding them back would recreate, inside the conversation, the very "deliverable nobody can find" the DONE branch was fixed for. **Every terminal is announceable**, CANCELLED included (`ANNOUNCEABLE` in `jobs/manager.py`): `cancel_job` is one of the four tools the model holds, so the same actor stops a job and reports on it — a stop that ends in silence is that defect coming back through another door. It is announced *as* cancelled, not as failed (this text is the model's instruction for what to tell the user, and a stop the user asked for is not a failure), and it carries `job.error` when there is one, since a cancelled job now can have a delivery note even though it has no failure message.
  - **Progress** ("background jobs still running" marker): one `progress_line()` per in-flight job ("2/4 steps done (research, documents) · running analysis · 3m elapsed"), derived from `plan` + `step_finished_at` alone — the job engine gained no bookkeeping for it. **Pushed, but only when it moved**: `progress_signature()` (status, plan size, steps landed — *not* elapsed time) is remembered in memory per session, so a stalled job costs nothing on the next turn and five turns of progress leave zero notices behind. Pull-only (`job_status`) was rejected: the model only calls it when the user thinks to ask, and the opaque wait is the bug. Cost: ~80 tokens on a turn that has news, 0 otherwise; `MAX_PROGRESS_JOBS` bounds both the tokens and the reloads (`list_jobs` returns summaries without the plan, so shown jobs are re-read with `get_job`).
- **Where the notices go is a provider constraint, not taste** (`_inject`): both notices go **directly after the system prompt**, never appended last or slotted before the final turn, because adjacent-to-the-leading-block is what `langchain_anthropic._format_messages` hoists into the top-level `system` param — a notice arriving there is read as an instruction, not as a message sitting inside the conversation, which is the semantics a status line needs. That placement is the one still asserted (`tests/test_chat.py::assert_notices_hoisted`), and the constraint is narrower than it once looked: `_format_messages` raises *"Received multiple non-consecutive system messages"* for a `SystemMessage` off that block on every version and on any model without mid-conversation system support, and langchain-anthropic 1.7.3 still raises it for one slotted anywhere non-adjacent short of the very end of the list — only a notice landing at the absolute tail, with nothing after it, is now silently accepted there as a trailing conversation turn instead, and only for the short list of models (`claude-opus-5` among them) the library now credits with mid-conversation system support. Silent is still the failure mode worth guarding, so the placement stays: it is what keeps every notice hoisted rather than merely unrejected. Anthropic hoists all system content into the top-level `system` param, so adjacency costs nothing; the conversation is left untouched, so the user's message stays the last message and a status line is never mistaken for the turn being answered.
- Tests script the model with `conftest.ScriptedChatModel` (AIMessages with `tool_calls`, `bind_tools` no-op, records inputs in `.calls`; **it implements `_astream` and really emits several chunks** — a model with only `_generate` makes LangChain fall back to a one-chunk `astream`, and every streaming test would go green while proving nothing) — which is exactly why the assembled message list must ALSO be run through the real provider formatters (`langchain_anthropic.chat_models._format_messages`, `langchain_openai.chat_models.base._convert_message_to_dict`, `pytest.importorskip`-guarded: the chat extras are optional). No network needed, and it is the only thing that catches a message list a provider will refuse. `_format_messages` is private and moves under this project's feet — 1.7.3 made `model` a required keyword-only argument (it decides whether the model supports mid-conversation system messages), which `tests/test_chat.py::format_for_anthropic` calls compatibly across both by inspecting the signature; these two tests are skipped outright without the chat extras (`pytest.importorskip`), so a drift like that is invisible to a plain `make check` and visible only in CI, which installs every extra.

### HTTP API (`api/`)

`create_api(service) -> FastAPI` (extra `.[api]`; served by `jobsmith serve`, whichever agent is composed). A pure adapter: every route is serialization plus one `AgentService` call — if job or chat logic reappears here, it belongs in `service.py`.

- **Chat**: `POST /sessions` → id; `POST /sessions/{id}/messages` returns `{"type": "message"}` or, where the gate was kept (`$JOBSMITH_APPROVE_JOBS`), `{"type": "proposal"}` (HITL interrupt surfaced over HTTP); client answers with `POST /sessions/{id}/approval {"approved": bool}`. A task runs inside the turn (#83), so a request here can last as long as the task — the adapter gained nothing for that, because a turn's duration was never its business. Both have a `/stream` twin (`.../messages/stream`, `.../approval/stream`) answering the same turn as SSE, event by event, ending on that same reply — additive, and what `DaemonClient` actually consumes (its `send` drains it). No queue behind them, unlike `/events`: the body is pulled from the turn itself, so a slow reader back-pressures through the socket into the model call and the answer stays whole. Unlike `/events` they *are* testable through `ASGITransport` — a turn's stream ends, so the buffering that hangs on an endless body is merely a delay here, and `tests/test_service.py` drives the event-by-event parity of both backings over it.
- **Jobs**: `GET /jobs[?session_id&status]`, `GET /jobs/{id}` (plan/step_finished_at/results — the UI's DAG data), `POST /jobs` (direct launch), `POST /jobs/{id}/cancel`, `POST /jobs/{id}/resume` (409 when the job has nothing left to run — `AgentService.resume_job` answers refusals as `{"status", "error"}` on both backings, so `DaemonClient` maps the code back into that dict).
- **Outputs**: `GET /jobs/{id}/outputs` lists the produced files, `/outputs/{name}` downloads one, `/report` is the inline shortcut to the main deliverable. `/report`'s content type is derived from the main output's `format` (`REPORT_MEDIA_TYPES` in `api/app.py`, unknown ⇒ `text/plain`) — mapping domain vocabulary to an HTTP header is the adapter's job, which is why the table is not in `jobs/report.py`. It serves *text* formats; a binary deliverable belongs on `/outputs/{name}`, whose `FileResponse` infers the type from the extension — and since #34 that is enforced rather than documented: `LocalAgentService.get_report` raises `BinaryDeliverable` (`service.py`) and the route answers **415** with the message naming that download. A 404 was the wrong refusal (the job *has* a report) and a redirect the wrong shortcut (a client could no longer tell the inline page from the file). The refusal is part of the port, so `DaemonClient` maps 415 back into the same exception with the same message, `jobsmith report` and `/report` in the REPL print it instead of "no report available", and `tests/test_service.py` pins the two backings to identical wording. The service refuses on two grounds — the format the output declares (`is_binary_format`) and a `UnicodeDecodeError` from the read itself, so a Reporter added later that forgets to declare `binary` still answers truthfully.
- **Live**: `GET /events` — SSE over `JobManager.subscribe()`: every `_persist_summary` emits `{job_id, status, steps_done, report_path, ...}` to subscriber queues (`put_nowait`, drops on full — never blocks a run; in-process only — cross-process events are #100, while cancellation crosses processes since #10). SSE can't be exercised through httpx `ASGITransport` (it buffers the whole body, so streaming `/events` through it hangs rather than fails) — the pub/sub is unit-tested in `test_jobs.py`, endpoints in `test_api.py`, and the one test that must cross a real stream (`DaemonClient.subscribe`, since #48) runs the app under **uvicorn on an ephemeral port**; its scripted cousins use `httpx.MockTransport`, where a body a well-behaved daemon does not send is deterministic.

### Terminal UI (`tui/`) — the first UI, and why it is a TUI

`jobsmith ui` (extra `.[tui]`, #48 step 2) is **a second presentation of the REPL's flow, not a second implementation of it**: it drives `stream`/`stream_approval` on `AgentService` and renders the same six events of `chat/runner.py`. It sits **beside** `jobsmith chat` and never replaces it — a TUI takes the whole screen and cannot be piped, and this CLI keeps stdout pipeable on purpose. It exists because of something the REPL cannot fix: `run_repl` blocks on `loop.run_in_executor(None, input, ...)`, so nothing repaints while it waits and a running job is invisible until the human types. Textual owns the event loop and treats a keystroke as an event, so progress is visible and free — the middleware keeps its purpose (the *model* sometimes needs to know a job finished), the opaque wait stops being the human's problem. Three panes: chat (the streamed turn, tool activity as prose, the job notice as a card to read, the HITL proposal as a card to answer where the gate was kept), the job list (`list_jobs`, which answers with **summaries** — no plan, so a row says what a summary knows), and the job detail (`get_job` for the DAG and the per-step table, `list_outputs` for the files). All of it follows the job on its own: `subscribe()` drives the repaint (#48 step 3), so there is no poll and no timer anywhere in this layer.

- **The stylesheet speaks standard theme roles and never a private vocabulary.** This is not taste: an invented variable name is not a wrong colour, it is `UnresolvedVariableError` **at parse time** — measured, the app does not even compose, under our own theme as much as under a foreign one. Chrome and state are two different accents (`$text-primary` dresses the tab bar and headings, `$text-accent` says "this is running"), because an earlier draft spent `primary` on both and the accent was gone on decoration before it reached the information. `themes.py` registers four of our own (`ember-*`, `tide-*`) beside Textual's 21 in the same Ctrl+P picker; `pick_theme()` follows `pick_db()` (argument > `--theme=` > `$JOBSMITH_THEME` > `ember-dark`), and a theme picked at runtime deliberately does **not** persist — that would be this project's first configuration file.
- **CSS says `$text-muted`, content markup says `$foreground-muted`.** The `$text-*` muted pair is `auto NN%` — a contrast computed against whatever background it lands on. A stylesheet knows that background and composites it; **markup does not, and drops the alpha**, so `[$text-disabled]` renders pure white on a dark theme. Every role in `render.py` travels as markup, hence the concrete `$foreground-*` pair there.
- **An undefined variable in markup does *not* raise — it is silently dropped and the text renders unstyled**, which is the opposite of the CSS rule above and is why the colour test checks role names as well as rendering. It matters because two built-ins really are short one: `ansi-dark` and `ansi-light` generate a reduced variable set with **no `$foreground-disabled`** (and `$surface-active` misspelt `$surface-actrive`). Under those two, queued steps and rules lose their dimming — cosmetic, and written down in `tests/test_tui.py` as what each theme is allowed to be missing, so the day Textual defines it the test keeps passing rather than inverting.
- **Status glyphs are in the job list and nowhere else.** `●` `◐` `○` are East-Asian-Ambiguous width: a terminal that renders them double-wide shifts every character under them, which the plan drawing cannot survive. The list has no alignment to keep and is the one place a colour-blind reader has nothing else to go on, so it carries both; everywhere else state is colour alone.
- **One keystroke never stops a job the screen has not shown.** `_selected` defaults to the first row and `list_jobs` sorts newest first, so a global cancel key would have killed the job just launched, from a pane that never displayed it. F8 is scoped to the jobs pane and arms first: the second press cancels, `escape` or moving the highlight disarms.
- **A job started in the turn is a card, not a line on the activity bar** (#83). `JobNoticeCard` and `ProposalCard` share `_job_body`, so the notice and the (kept) proposal show the user the same three things and neither can quietly drop one. It is mounted into the conversation because the activity line is overwritten by whatever happens next, and what a run was handed is the part someone may need to read again — a file they did not mean to hand over, a document named something they did not ask for. `self._answer` is reset when it mounts, or the tokens that follow would be appended to the bubble *above* the card. This is also where this UI stops being a convenience: a task now runs while the person waits, and the jobs pane fills in the plan as it does — which is exactly what the REPL cannot do because it blocks on `input()`.
- **A turn in flight refuses new input rather than being cancelled by it.** `@work(exclusive=True)` means a second submit cancels the first, which left half an answer on screen with nothing saying it was cut — the exact defect `ChatStreamError` handling exists to prevent, and worse: a turn cancelled just before its `proposal` leaves the thread interrupted in the checkpointer while `_awaiting_approval` is still false, so the next message goes down `stream()` and never answers it. The REPL cannot reach this because it blocks on `input()`. Both refusals — mid-turn, and an ordinary sentence typed while a proposal waits — **keep the text in the box**: the alternative is losing something the user wrote. Only `y/yes/o/oui` approve and only `n/no/non` (or a bare Enter, the `N` the prompt advertises) decline; anything else is refused, where the REPL could read it as a decline because its prompt is a separate line rather than the same box.
- **An event says *something changed*, never *what* changed.** `subscribe` drops under back-pressure on both backings — by design, since the next tick supersedes the one nobody saw — so a UI that accumulated deltas would be wrong exactly when it was busy. `_watch` re-reads instead (`list_jobs`, then `get_job` and `list_outputs` for the row on screen), which makes a dropped event cost a slightly later repaint and nothing else, and coalesces a burst into one pass. It is a plain `asyncio.Task` rather than a Textual worker for a test-shaped reason that is also the truth about it: `workers.wait_for_complete()` waits for every worker, and this one is over only when the app is. It is cancelled and awaited in `on_unmount`, because a subscription behind a daemon is an open HTTP stream and not a reference.
- **A refresh in flight is joined, never cancelled — and never dropped either.** A refresh is three calls against a daemon and events arrive faster than that when a wave lands; `exclusive=True` would have each one cancel the last, so the list never repopulates and a cancellation landing on `clear()` leaves it empty. Skipping alone was enough only while a poll re-armed two seconds later: with nothing re-arming, the request most likely to be dropped is the *last* one, the event that says the job is DONE. So a skipped request is remembered and the refresh goes round once more.
- **The end of the stream is carried on the queue, because stderr is not a screen.** `None` is the port's marker for "nothing more will arrive here" (`service.py`), and the remote reader puts it there even on a full queue — evicting the oldest tick, since the drop rule exists because the next event supersedes the dropped one and nothing supersedes this. `DaemonClient` also prints a line, which is right for a command and unreachable for a UI that owns the terminal, so the TUI says it on the tab bar and in a notification: a screen that stopped following must not look like one that is up to date.
- **A backing that raises does not take the screen down, and the screen says why** (#64). Killing the daemon and pressing F5 used to end the app while the user was looking at it: `list_jobs` raised inside the `reload` worker and Textual reraises a failed worker into the app. The answer is not a broad `except` around every call but the port's own `ServiceUnavailable` (see `service.py`), caught by name at the three places this layer calls out — the `reload` worker, the highlight handler (a message handler, not a worker), and the streamed turn — so a `KeyError` in *our* code still ends the app loudly, which is where a defect belongs. What it does with it is #57's state, because the reasoning is #57's: a daemon that vanished is not one pane's error, nothing will work until it is back, and what is already on screen was true when it was read. So the tab bar carries the stronger of the two facts (`UNREACHABLE` over `LIVE_LOST`, one slot), the notice is said **once per outage** rather than once per failed call (an event burst would otherwise stack a wall of toasts over the screen it is warning about), and a call that gets through clears it — but never clears `_live_lost`, since nothing resubscribed: up to date at this instant and still not following is exactly what the tab bar then says. Nothing retries on its own; a reconnect loop against a daemon that is gone is a spinner pretending to be progress, and F5 is one keystroke. A turn that dies mid-sentence says so **in the conversation** as well, because that is where the person is looking. Asserted by name in `tests/test_tui.py` — `app.is_running` after F5, and the note on the tab bar — since a snapshot would happily bless a screen that had stopped saying anything.
- **The artifacts pane locates a file and never offers it.** It reads `list_outputs` (the only call carrying `JobOutput.name`, see below) and shows the path with one line saying whose disk it is on, from `service.mode`: with a daemon backing those are the daemon's paths, true and unopenable from here, so the pane names `GET /jobs/{id}/outputs/{name}` instead of implying a file the reader can reach. `find_output` is what turns a record into an answer about the file — a deliverable deleted since the job finished reads as gone rather than as a path to nothing — and it is one round trip per file, so it is asked once per *set* of files (which changes when a step produces one, never between two events about the same step); F5 asks again from scratch.
- **`Job.to_dict()` is `dataclasses.asdict`, which drops properties.** `JobOutput.name` is one, so `get_job` carries `path` and no `name` — only `list_outputs` adds it back, which is why the artifacts pane is fed by that call and not by the job it is already holding. The pane read the missing key and printed a blank filename on every job, and the layout snapshot was generated from that and froze it as correct. Hence the rule below about what a snapshot may be asked to prove.
- **The plan is drawn by accumulating directions per cell.** `render.dag()` places nodes on a character grid by wave column, then each edge records a set of N/S/E/W per cell it crosses and the box character is chosen once at the end — which is what makes a crossing a junction (`┬`) instead of whichever segment was drawn last. The columns are `core.state.plan_depths`, extracted there and shared with `jobs/report_html.py::dag_svg`: two drawings of one plan must agree on where a step belongs, and a second copy of the longest-path relaxation is where they would stop agreeing. Accumulation answers "what meets here" and cannot answer routing, so two things are decided before it runs: **each source owns a vertical** (steps of one wave with equal-length names shared a trunk, and their edges merged into one line going somewhere neither went), and **an edge spanning more than one wave detours through the row below its target** (drawn straight it crossed the *names* in between, and a name is never overwritten, so it read as entering one step and leaving another — odd rows carry no names). What is left is named in the docstring rather than half-fixed: an arriving edge must cross the band of verticals leaving its target's column, so two edges that genuinely cross there merge into one `┴`. Undoing that is lane routing — a track per edge — which is a layout algorithm, not a guard.
- **Bindings are function keys, and that is forced.** A focused `Input` has first refusal on every key it binds — ctrl+x, ctrl+k, ctrl+w, ctrl+u, ctrl+d are all editing commands there, so a binding on any of them never reaches the app (reproduced: ctrl+x cancelled nothing while the prompt had focus). ctrl+j is worse than taken: it *is* the newline control code, so binding it steals Enter from the prompt.
- **A step's `took` is derived and says so.** The record holds when a step *finished* (`step_finished_at`) and never when it started, so `render.step_states` reports the window between the step's dependencies landing and the step landing — an upper bound on its own time. Adding start timestamps is a change to the job engine, not to a drawing of it.
- **Model text is escaped before it becomes markup.** A `Bubble` repaints `escape(text)` on every token and a job's request is escaped in every row: content markup is `[...]`-delimited, so an unescaped answer could open a tag in the UI drawing it — the same rule `report_html.py` follows with `html.escape`.
- **Two kinds of test, and they answer different questions** (`tests/test_tui.py`). A **snapshot** (`pytest-textual-snapshot`, SVG) pins *layout*, so one theme is enough and a second would only be another file to regenerate. **Colour** is one test that loops every registered theme, mounts both panes, renders for real and checks the role names resolve — it costs the same for 25 themes as for two. And a snapshot is never asked to prove a *fact*: it blesses whatever it is shown, including a field that renders empty, which is how the blank filename above passed review — so what a pane must say is asserted by name, and the jobs snapshot checks the filename is on screen **before** the picture is taken, so `--snapshot-update` cannot re-freeze the bug. Both were falsified: an invented CSS variable makes the colour test fail with the parse error above, an invented markup role makes it fail by name, and a changed pane width makes the snapshot fail. The behaviour tests drive the real `LocalAgentService` with `conftest.ScriptedChatModel`, so "the answer is drawn as it arrives" is a claim about prefixes of a growing bubble — a turn rendered in one block leaves exactly one. **`pytest-textual-snapshot` is pinned to an exact version** (`make snapshots` re-accepts a deliberate layout change): the snapshot names and format belong to the tool, and **CI installs from `pyproject.toml`, not from `uv.lock`**, so a range is enough for the two to disagree — measured, a range gave 1.1.0 locally and 1.0.0 in CI and every stored snapshot came back "unused". That pin caps pytest below 9, which is the honest price of it.

### Adding a capability

1. Subclass `Capability`; define `spec` (unique snake_case name), constructor taking needed clients, async node methods, `build()` via `self.state_graph(...)`, terminal nodes returning `self._emit_success(...)`/`self._emit_failure(...)`, and `render_context()` if its result should feed generation.
2. Register it in the composition root before `AgentBuilder(...).build()`. Nothing else: planner prompt, dispatch, merging all pick it up from the registry.
3. If it needs to **read** a file the request named (`agents/default/read_files.py` is the shipped example): declare `requires_inputs=(SOURCE_FILES_INPUT_KEY,)` so the planner drops it when nothing was named, take a port in the constructor and never `Path.read_text` — and let that port refuse; what a path may be is `core/paths.py`, and the roots are the deployment's (`AgentContext.readable_roots`).
4. If it needs what an **earlier job** produced (`agents/default/prior_jobs.py` is the shipped example): declare `requires_inputs=(FROM_JOBS_INPUT_KEY,)`, take the `PriorJobSource` port (`ctx.prior_jobs`) in the constructor and never reach into `jobs/` — and bound what travels, because a previous run's results are tens of thousands of characters and every cut has to be written into the text. Who may reference what is settled where the reference is accepted (`chat/tools.py` scopes it to the session), never here.
5. If it produces a **file** (`agents/default/slides.py` is the shipped example): take an `ArtifactStore` (`ctx.artifacts`) in the constructor, `await self.artifacts.write(state.get("job_id", ""), "chart.svg", data)`, and pass `meta=artifact_meta(ArtifactRef(path, title="…"))` to `_emit_success` — or to `_emit_failure`, if it wrote the file and broke afterwards. The job lists it as an annex whatever terminal the run reaches; never build a path yourself — `reports_dir` is the manager's.

## Testing conventions

- `tests/conftest.py` — `FakeLLM` scripts responses by **substring of the system prompt** (`{"planner": ..., "ONLY the provided": ...}`); `plan_json()` builds planner responses. Fixtures: `checkpointer` (MemorySaver), `store` (InMemoryStore).
- `tests/test_banking_example.py` is the behavior-parity suite for the pre-refactor agent (French rejection messages, citation rule, vision-dropped-without-image).
- Tests import capabilities/stubs directly and assert on the final state dict (`terminal_kind`, `results`, `completed_capabilities`).
- **The default registry is configuration-dependent**, so a test that pins what `KeywordLLM` plans (it chains every registered capability) must ask the composed app what it registered — `conftest.registered_capabilities(app)` — instead of hardcoding one environment. **Registered is not planned**: a step gated on `requires_inputs` (`read_files`) is in the registry and in the fake's chain, and the planner then drops it for a request carrying no such input, so that helper answers with the *ungated* set (`gated=True` for the whole registry) and `AgentApp.registry` is what lets it tell them apart. `slide_deck` made this real: with `.[pptx]` installed the fake plans a fourth step, and a hardcoded `{"research", "analysis", "critique"}` then passes under `make install` and fails in CI. The **order** of the registry is load-bearing for the same fake: it chains the capabilities as listed and plan validation prunes a dropped step's name from the surviving `depends_on`, so a gated step listed in the middle silently severs the chain around it — which is why `prior_jobs` and `read_files` are first in `default_capabilities` and why `grounding_reaches_reasoning` went to a *skip*, not a failure, when they were not.

## Evaluating prompts (`evals/`)

A prompt change (router, planner, generator, a capability's own instructions) is
not judged by eye here: `make eval` scores it on a golden set of requests and
prints a table comparable with the previous run.

- **Properties, not expected text.** Nothing asserts an answer. The checks are
  structural: the plan names only registered capabilities, is duplicate-free,
  acyclic and has satisfiable dependencies; an obviously simple message is
  triaged `direct` and a compound one `plan`; the run reaches the expected
  terminal; every planned step ran and reported ok; the deliverable has a title,
  the answer and the job that produced it. `scoring.py` holds one
  function per property, each returning pass / fail / **skip** — skipped checks
  leave the denominator, so a direct-route case never dilutes the plan checks.
- **The report checks are format-independent, and now really are.** They read
  the deliverable through `deliverable.extract(text, format)`, which returns
  the title and the visible text with the markup stripped, and compare needle
  and haystack after the same `normalize()` — so `- **web_search**` and
  `<li><strong>web_search</strong></li>` are one string. Before that they were
  markdown-shaped while the docstring claimed otherwise (`# ` is not how HTML
  opens; escaping moved the strings they searched for), and the golden set
  scored 13 checks lower in HTML purely on the format. `--report-format html`
  scores the other Reporter, and `tests/test_evals.py` pins the two runs to
  identical per-check tallies. An unknown *text* format is read as plain text:
  a new text Reporter is scored on its content from day one, only its *title*
  needs an extractor here. A format whose file is **bytes** has no such
  reading, so it is refused at the entry (`deliverable.ensure_readable`, the
  lookup being `is_binary_format` — evals grows no second list of what is
  text) rather than scoring ~2/10 on the format and storing a record the next
  run would pick up as its baseline (#45). It is asked of the *first* format,
  which is the `main` output and therefore the only file the checks read, so
  `--report-format markdown,pdf` still scores markdown honestly.
- **Two tiers.** `structural` runs on `KeywordLLM` — no key, no variance — and
  is expected to be 100%: `tests/test_evals.py` asserts exactly that, so a
  prompt edit that breaks the machinery fails `make check`. `llm` needs a real
  provider, tolerates variance and **never gates CI** (`python -m evals` exits
  non-zero only on the deterministic fakes — the provider is the condition, not
  the tier label — or with an explicit `--fail-under`).
  A case declares which tiers it is meaningful in: one a keyword fake would pass
  or fail *by accident* is llm-only, otherwise the fake is what gets measured.
  **The fake tier is only deterministic if no key reaches the process**, and
  `python -m evals` loads `.env` (which `make worktree` copies) with
  `os.environ.setdefault` — so `env -u TAVILY_API_KEY` is refilled from the
  file and `web_search` quietly joins every plan (measured: 147/160 instead of
  153/153, the extra checks being web material the fake cannot trace). Blank
  the keys instead: `TAVILY_API_KEY= ANTHROPIC_API_KEY= OPENAI_API_KEY=`.
- **The harness runs the real product path** (`harness.py`): `build_app` →
  `create_job` → `run_job`, persistence forced to `memory`, reports into a
  scratch dir, a `KeywordChatModel` injected only so composition does not go
  looking for chat extras. The triage decision is read back from the
  checkpointer (`graph.aget_state`), because a planner rescuing a message the
  router should have sent direct is invisible from the outside. The
  generator's **merged context** is read back from the same snapshot (#73):
  a `Job` records what came out, and "was the deliverable built from the
  material" is a question about what went in.
- **Runs are stored, not just printed** — `evals/results/*.json` (gitignored),
  tagged with agent, provider, tier, case set, report format and git rev; the
  next run matching the first four is picked up as a baseline automatically and
  rendered as a Δ column. A `--case` slice is therefore never a baseline for the
  full set. The report format is recorded but deliberately NOT part of that
  match: the checks score the same property either way, so an HTML run is a
  legitimate baseline for a markdown one — which stays true only because every
  run that reaches storage scored a text deliverable, the refusal above being
  what guarantees it.
- **`must_include` has a mirror.** `must_exclude` names capabilities the plan
  must NOT contain, scored by `plan_excluded_steps` — the only way to measure
  a spec that is too easy to reach (#61), since such a run is green end to
  end and the user simply opens the wrong kind of file. It skips when none of
  the named capabilities is registered, like its mirror. It is exercised in
  the *structural* tier by `plan_report_request` excluding `read_files`: the
  fake chains the whole registry, and plan validation drops that step as
  inapplicable because no file was named — so the deterministic tier measures
  the dropping, and a case excluding a step the fake would really plan
  (`slide_deck`) is llm-only, or it would measure the fake.
- **Two checks read the deliverable's substance, and one of them reads its
  input** (#73). `report_reader_facing` catches a document addressed to the
  wrong reader; nothing caught a document with no answer in it, which is how
  a run scored 100% here while delivering a data-collection plan.
  `report_answers_request` asks two things at once, because either alone is
  free: the answer names most of the request's own content words *minus the
  vocabulary of producing a document* (`compare X and write me a report` is
  about X), **and** it carries a third of what the material keeps coming back
  to — the half a restatement of the brief cannot fake, which is exactly why
  it is measured against the generator's input and not against the request.
  `refusal_is_bare` is the twin of `refusal_declared` and scores a shape:
  short, no blank form, no plan or offer of service. Both read the *answer*,
  never the file — a Reporter's provenance is about the run by design and
  quotes the request. The term machinery (`terms`, `frequent_terms`,
  `STOPWORDS`, `PROCESS_WORDS`) lives in `deliverable.py` with `normalize`,
  and is deliberately blunt: a bag of words with no stemming, thresholded at
  a third, so a missed stopword makes a check more lenient and never wrong.
  What neither detects is the opposite failure — a generator that dumps its
  context scores perfectly on both.
- **One check reads what the steps produced, not what the document says**
  (#81). `report_answers_request` was green through the entire run that
  opened that issue: the merger hands the retrieved material straight to the
  generator, so the deliverable carried it while not one step between the
  retrieval and the writing had read it.
  `grounding_reaches_reasoning` asks the same question one layer earlier and
  against the steps' own `results` — a third of what the retrieved documents
  keep coming back to (minus the request's own words) has to appear in what
  the steps downstream of the retrieval produced. It recognises a retrieval
  step by the **shape** of its result (`data["documents"]`, passages with a
  `text`) and never by name: `evals` is agent-agnostic, and a check that knew
  `web_search` would score one pack and silently skip every other. Three
  honest skips, each leaving the denominator: nothing was retrieved, the
  retrieval failed, or **no step of the plan depends on the retrieval** — the
  last one being the limit worth naming, since this measures the edges a plan
  *draws* and a plan that schedules retrieval beside reasoning draws none.
  Like every check built on `frequent_terms` it detects abandonment and never
  regurgitation.
- **A case can name a file, and it cannot carry a path** (#81). The check
  above needs a run with real material, and the only grounding step that is
  deterministically available is `read_files` (`documents` and `web_search`
  need a `--docs` directory or a key; `documents` searching a fixture corpus
  on *every* case would fail the step wherever no term overlapped). So one
  golden case names a file — and `read_files` may only open a path inside a
  root the deployment declared, which under `build_app` is the scratch
  reports directory this suite composes. A case therefore declares
  `FIXTURE_REF` in its `inputs`, `harness.write_fixture` writes the fixture
  there before the app is composed, and `resolve_inputs` swaps the real path
  in: a hard-coded path would be a path to one machine. The fixture text is
  short, specific and domain-neutral on purpose — short so that what a step
  did with it is legible in that step's own output, specific so that "this
  reached the reasoning" is a question a bag of words can answer at all.
- **`document_format` scores what the request asked for, in words** (#90), and like `document_as_requested` it is scored against the **case**: a job records the format it chose, so asking the record whether that was right is asking the defect to report itself. `EvalCase.expect_format` is the claim, and a format this deployment cannot render is a **skip** — `.[pdf]` needs pango where the run happens, so a golden case must not score a machine (`Observation.formats_available`, composed once per suite). The structural case asks for HTML rather than PDF for that same reason, and `KeywordLLM` reads the format names back out of the rendered prompt (`FORMAT_LINE`) and matches them against the request, exactly as `DIRECT_WORDS` lets it exercise triage — so the deterministic tier measures the wiring and never the fake's taste.
- **The deliverable's contract changed, so two checks did** (#85). `report_provenance` asked for the job id **and** the request quoted back, and `report_covers_plan` for every executed step to be named: both encoded the *About this job* section, which a reader no longer opens. `report_provenance` now scores the one property that survived and could not be got anywhere else — the file names **which run wrote it** — and it is what fails, in both formats and on the deterministic tier, if the footer is ever dropped. `report_covers_plan` was **removed rather than inverted**: the honest inverse is "no step is named", and `research`, `analysis`, `documents` and `critique` are ordinary words a document about a subject uses legitimately, so a substring test on their absence would score the prose and not the machinery. What a plan did is the *record's* question, and `GET /jobs/{id}` is what answers it. Nothing else moved: the structural tier stayed 100%, and every remaining check still applies to at least one golden case.
- **The answer is scored wherever it is delivered, the file only where one was asked for** (#96). When a silent request stopped getting a file, most of the golden set did too — and a skip is not a failure, so the tier went on reading 100% while `report_reader_facing` and `report_answers_request` fell from **7 applicable runs to 2** and `refusal_declared` to **0** (measured on the engine change alone, before the evals moved; only the every-check test noticed the last one, and nothing noticed the first two). The gate was the defect: CLAUDE.md already said those checks read the *answer*, never the file, yet they sat behind `_report_applies`. They now go through `_answer_applies` — the run answered **from a plan** — and keep their `report_` names only so stored runs stay comparable. The plan condition is #80's guard falling out for free: a `DirectResponder` reply is a chat turn by construction, and scoring its register as a deliverable's is the confusion #80 names, including when a file was asked for. `refusal_is_bare` was already ungated. What reads the FILE (`report_written`, `report_title`, `report_answer`, `report_provenance`, `refusal_declared`) stays on `_report_applies`, and got golden cases that ask for one: `plan_report_request` ("produce a report", no format — the one request `$JOBSMITH_REPORT_FORMAT` still answers), the new `plan_document_requested_without_format`, `plan_html_page_requested`, and the new `unanswerable_as_a_document`, without which the declaration in a refused deliverable would be scored on nothing. The silent planned cases now *claim* `expect_document=False`, so `document_as_requested` scores the new contract on 11 runs. After: answer checks 8, file checks 3, `refusal_declared` 1, 168/168. "Every check applies somewhere" could not see a check falling from 7 to 2, so `test_the_answer_is_scored_on_more_runs_than_the_file` pins the shape instead — the answer checks apply to every planned answered case, strictly more than the file checks, and the golden set carries silent requests, requests for a file, and a refused request for a file. `KeywordLLM` recognises "a report" / "a document" as that fourth document answer, the same crude way it recognises format names — narrow on purpose, since "the attached quarterly report" is material and not a request for one.
- Adding a case is one `EvalCase` in `cases.py`; adding a property is one
  function in `scoring.py` plus its name in `CHECK_NAMES` (a test pins the two
  together). Cases stay **domain-neutral** — `make leak-check` scans `evals/`
  too; an agent-specific golden set would live with that agent.
- **The structural tier must exercise every check** (`test_structural_tier_actually_exercises_every_check`): a check nothing applies to protects nothing. #73's two checks needed no new case — the fake's answer echoes the material it was handed, which is exactly what `report_answers_request` measures, and `unanswerable_missing_material` already reaches the `unanswered` terminal for `refusal_is_bare`. #81's needed one, because no existing case gave the run any material to trace (see the fixture bullet above); it is scored on the fake for the same reason #73's are — the fake echoes what it is handed, so a step that was handed the material says so and a step that was not cannot. `refusal_declared` (#59) is the case that made this bite — the fake has no notion of insufficient material, so `KeywordLLM` recognises the one shape it can (a request leaning on material nobody supplied, `MISSING_MATERIAL_WORDS`) exactly as `DIRECT_WORDS` lets it exercise triage, and one golden case reaches the `unanswered` terminal deterministically.
- **Say what it is worth.** Eleven cases sampled once from a stochastic model is
  a smoke signal, not a benchmark; the structural tier is the only part that is
  actually reliable, and it only proves the machinery holds.
