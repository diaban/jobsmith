## From “Agents (`agents/`) — what an agent *is*”

**`prior_jobs` is the THIRD referent, and it is not a file at all** (#74): *"make a one-pager out of that report"* used to reach `read_files` with the path of the document the previous run wrote, so this product re-read through the filesystem a file it had written itself minutes earlier. Four things were wrong with that round trip and only the first is about elegance. **The report is a deliverable, not a trace** — per-step material is deliberately not inlined into it — so re-reading it is reading the *thinnest* representation of the run: the final prose, never `research`'s notes nor `web_search`'s passages (measured: the deliverable of a run whose deliverable was a work plan, re-read, inherits the work plan and none of the material actually gathered). **#85 made that argument stronger**: the file is now a title, the answer and one `job_reference` line, so it carries nothing `final_answer` does not — re-reading it is reading the answer through a filesystem and losing every step's material on the way. (It also removed what was a fifth argument when this was filed — the *About this job* section coming back as if it were subject matter — because that section is gone.) It **assumes a file that exists, is text and is on this machine**, which is exactly what `find_output` refuses to promise (#49), and a PDF deliverable cannot be read back at all. It needs a **path policy for a case with no path**. And since #84 a run leaves a document only because the request asked for one, so the file may never have been written: the round trip is not merely worse, it is sometimes impossible. So a job reference is a second *input* (`inputs["from_jobs"]`, `FROM_JOBS_INPUT_KEY`) and a second **port** — `PriorJobSource.load(job_id) -> PriorJob` (the answer plus the per-step material, in plan order) — never a widening of `DocumentReader`, for the reason #60 gave about `DocumentSource`: a request naming a file and a request naming a run are two questions, and one step with a mode answers neither well. Its decisions: **the port lives in `core/prior_jobs.py`, not beside the capability**, unlike `DocumentSource`/`DocumentReader` — the composition root supplies it (job records are the deployment's persistence, not an agent's document index), so `AgentContext` has to name it and `agents/base.py` may not import one agent's module, which is the argument that already put `ArtifactStore` in `core/artifacts.py`; the adapter is `jobs/prior.py` (`RepositoryPriorJobs` over `JobRepository`, the only place that knows plan order and where an answer lives) and the capability imports neither. **It calls no model and a refusal is material** — both `read_files`' rules, for the same reasons. **A job that exists and produced nothing is not a missing job**: the port carries `status`, so "queued" and "no such job" are told apart instead of both reading as "that run established nothing". **Its result is shaped like a retrieval step's** (`documents` with quotable `<short id>#answer` / `<short id>#<step>` ids, `unavailable` beside it), which is what lets `research.GROUNDING` and `REFUSALS` read it through the machinery #81 already built rather than growing a second one — a follow-up whose notes are written from memory about a job it was handed is #81's defect arriving through the other door. **The material is bounded at 24 000 characters ≈ 6 000 tokens** for all referenced jobs together (one measured job carried 44k across four steps, and this block is re-sent by `research` and then the generator), shared out block by block so nothing is dropped whole and short blocks hand their share back, each cut written into the text — the rule `TavilySource._bounded`, `LocalFileReader` and `research` all follow. The **answer gets first claim on half of it**: it is the one thing a re-read of the file *would* have given, so it must not be the part the steps squeeze out. At most 3 jobs are read and the rest are named as dropped. **The scope is the session's own jobs, enforced in `chat/tools.py`** — `launch_job` takes `from_jobs` and resolves each reference through the same `_find` every other job tool uses, so what reaches the engine is a full id of this conversation's jobs and a reference that resolves to nothing is refused *before* the run, in words the model can act on. It is there and not in the port because the job engine never sees the conversation and the adapter is composed once per app: an id arriving through `POST /jobs` carries no asker, which is a fact about that door (it has no session boundary of its own) and is written down rather than papered over. **The two gated steps are at the FRONT of the registry list**, which is not cosmetic: `KeywordLLM` chains the registry in order and plan validation prunes a dropped step's name from the surviving `depends_on`, so a gated step in the middle severs the grounding→reasoning edge that #81 exists to make real.

## From “Core concepts (read these files first)”

**`core/prior_jobs.py`** — the `PriorJobSource` port: `load(job_id)` answers with what an earlier run produced (its answer, its per-step material in plan order) and touches no filesystem. It is here rather than beside the capability that consumes it for the reason `ArtifactStore` is: the composition root supplies it, so `AgentContext` must be able to name it. Nothing here names a store, a namespace or a schema — the adapter is `jobs/prior.py`.

## From “Jobs layer (`jobs/`)”

**`jobs/prior.py` is the adapter that hands a finished run's material back** (`RepositoryPriorJobs`, `PriorJobSource` over `JobRepository`, #74): it is the only place that knows a step's result is reached through the repository, that `ordered_results()` is what puts them in plan order, and that a failed step's `error` is what it has to say. Rendering is deliberately the dumb one — `default_result_markdown`, because the capability that produced a step's result may not be registered in the app reading it back.

## From “Chat layer (`chat/`)”

**A job the request builds on is referenced, not re-read** (#74): `launch_job` also takes `from_jobs`, and the docstring tells the model to prefer it over `source_files` every time the material came from a job of this conversation — the report that job wrote is thinner than what it produced, may be binary, and since #84 may not exist. **This is where the scope lives**: each reference is resolved through `_find` against *this session's* jobs, so `inputs["from_jobs"]` carries full ids the engine can trust and a reference matching nothing is refused before anything runs (the model can fix it in the turn, exactly as it fixes an impossible format). A job reference must not become a way to read another conversation's work, and the port cannot enforce that: it is composed once per app and an id arrives with no asker attached, which is the same reason the excerpt of the thread has to travel as an input. **What the notice does NOT yet carry is the reference itself**: `job_started` names the files a run may open (#60) and not the jobs it builds on, because the payload, `JobStarted` and both front-ends would each have to learn the field. That is a gap and not a decision against showing it — the mitigating fact is only that a referenced job was announced in this same conversation, where a handed-over file never was.

## From “Adding a capability”

If it needs what an **earlier job** produced (`agents/default/prior_jobs.py` is the shipped example): declare `requires_inputs=(FROM_JOBS_INPUT_KEY,)`, take the `PriorJobSource` port (`ctx.prior_jobs`) in the constructor and never reach into `jobs/` — and bound what travels, because a previous run's results are tens of thousands of characters and every cut has to be written into the text. Who may reference what is settled where the reference is accepted (`chat/tools.py` scopes it to the session), never here.
