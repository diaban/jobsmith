## From “Chat layer (`chat/`)”

- **Completion** ("background jobs finished" marker): final answer + report path for unannounced session jobs, marked announced *after* the model call succeeds. First of the notices — it is an instruction to act on now. A DONE job can have **no** main output (the run answered, the write failed), so `_notice_for` states the path when there is one and `job.error` when there is not, plus any file written before the failure — never `Report file: None`; the answer is announced either way, which is the point of staying DONE. A job that did **not** answer is announced with its error *and* the files its steps left behind (#41), labelled as partial material rather than a report: holding them back would recreate, inside the conversation, the very "deliverable nobody can find" the DONE branch was fixed for. **Every terminal is announceable**, CANCELLED included (`ANNOUNCEABLE` in `jobs/manager.py`): `cancel_job` is one of the four tools the model holds, so the same actor stops a job and reports on it — a stop that ends in silence is that defect coming back through another door. It is announced *as* cancelled, not as failed (this text is the model's instruction for what to tell the user, and a stop the user asked for is not a failure), and it carries `job.error` when there is one, since a cancelled job now can have a delivery note even though it has no failure message.

- **Progress** ("background jobs still running" marker): one `progress_line()` per in-flight job ("2/4 steps done (research, documents) · running analysis · 3m elapsed"), derived from `plan` + `step_finished_at` alone — the job engine gained no bookkeeping for it. **Pushed, but only when it moved**: `progress_signature()` (status, plan size, steps landed — *not* elapsed time) is remembered in memory per session, so a stalled job costs nothing on the next turn and five turns of progress leave zero notices behind. Pull-only (`job_status`) was rejected: the model only calls it when the user thinks to ask, and the opaque wait is the bug. Cost: ~80 tokens on a turn that has news, 0 otherwise; `MAX_PROGRESS_JOBS` bounds both the tokens and the reloads (`list_jobs` returns summaries without the plan, so shown jobs are re-read with `get_job`).

**Where the notices go is a provider constraint, not taste** (`_inject`): both notices go **directly after the system prompt**, never appended last or slotted before the final turn, because adjacent-to-the-leading-block is what `langchain_anthropic._format_messages` hoists into the top-level `system` param — a notice arriving there is read as an instruction, not as a message sitting inside the conversation, which is the semantics a status line needs. That placement is the one still asserted (`tests/test_chat.py::assert_notices_hoisted`), and the constraint is narrower than it once looked: `_format_messages` raises *"Received multiple non-consecutive system messages"* for a `SystemMessage` off that block on every version and on any model without mid-conversation system support, and langchain-anthropic 1.7.3 still raises it for one slotted anywhere non-adjacent short of the very end of the list — only a notice landing at the absolute tail, with nothing after it, is now silently accepted there as a trailing conversation turn instead, and only for the short list of models (`claude-opus-5` among them) the library now credits with mid-conversation system support. Silent is still the failure mode worth guarding, so the placement stays: it is what keeps every notice hoisted rather than merely unrejected. Anthropic hoists all system content into the top-level `system` param, so adjacency costs nothing; the conversation is left untouched, so the user's message stays the last message and a status line is never mistaken for the turn being answered.

Tests script the model with `conftest.ScriptedChatModel` (AIMessages with `tool_calls`, `bind_tools` no-op, records inputs in `.calls`; **it implements `_astream` and really emits several chunks** — a model with only `_generate` makes LangChain fall back to a one-chunk `astream`, and every streaming test would go green while proving nothing) — which is exactly why the assembled message list must ALSO be run through the real provider formatters (`langchain_anthropic.chat_models._format_messages`, `langchain_openai.chat_models.base._convert_message_to_dict`, `pytest.importorskip`-guarded: the chat extras are optional). No network needed, and it is the only thing that catches a message list a provider will refuse. `_format_messages` is private and moves under this project's feet — 1.7.3 made `model` a required keyword-only argument (it decides whether the model supports mid-conversation system messages), which `tests/test_chat.py::format_for_anthropic` calls compatibly across both by inspecting the signature; these two tests are skipped outright without the chat extras (`pytest.importorskip`), so a drift like that is invisible to a plain `make check` and visible only in CI, which installs every extra.
