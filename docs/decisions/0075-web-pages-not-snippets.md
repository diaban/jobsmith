## From “Agents (`agents/`) — what an agent *is*”

**`web_search` is the same capability pointed at the web**: `WebSearchCapability` lives in `documents.py` next to its parent, subclassed from `DocumentsCapability`, and `web.py` holds no capability at all — only the `TavilySource` adapter it is pointed at (as `sources.py` holds the `DocumentSource` port and `LocalFiles`). The subclass exists because the ONLY difference is the spec — and the spec is what the planner reads to choose between the user's own files and what the web says today. Gaining the web required no change to the consuming capability, which is what the port was shaped for. **What a result carries is the adapter's decision, and it was the wrong one** (#75): Tavily returns a relevance-cropped `content` snippet and, only when `include_raw_content` is asked for, the page's extracted `raw_content` — and the adapter asked for neither, so the step whose whole purpose is to ground a run outside the model grounded it in ten snippets (`max_queries=3` × `per_query=6`, capped at `max_documents=10`). Measured on one job: a request for spec sheets, warranties, prices and source links was **unreachable by construction**, and the run reported "the material is insufficient" — a statement about the world, made about our retrieval. The fix stayed inside the adapter, which is the point: `Document.text` simply carries more, `DocumentsCapability` learns nothing, the port is untouched, and none of it is chunking, embeddings or re-ranking. Three decisions came with it. **The page wins, the snippet is the fallback** — `raw_content` is null for a page Tavily could not fetch, and an excerpt grounds more than an empty document. **Depth is a deployment choice with an opinionated default**: `advanced` (`pick_search_depth`, `$TAVILY_SEARCH_DEPTH`, read where `$TAVILY_API_KEY` already is), because retrieval quality *is* the bug and `basic` is what produced snippet-shaped material; it costs more per call, so a deployment can lower it, and a value Tavily has never heard of raises in `TavilySource.__init__` — at startup, the rule `PdfReport` applies to its engine — rather than being sent on to be ignored server-side. **The bound lives where the bytes arrive**: `max_chars=8_000` per document, because `render_context` concatenates `d["text"]` with no bound of its own, so the worst case handed to it is 10 × 8 000 = 80 000 characters ≈ 20 000 tokens, re-sent by every downstream step that reads the merged context — where a whole page (50–100k characters) times ten would be ~250k tokens, more than the window before a single step has thought. The cut lands on whitespace and is **written into the text**, exactly as `LocalFileReader` writes its own: a page silently shortened reads to the model as a complete page, which is a new way to be wrong about the world. What that better material was worth was capped by something this issue could not see: until #81 it reached the generator and nothing else, so half of what #75 improved was never wired.

`TavilySource` is the **first adapter that must be closed**: its `httpx.AsyncClient` is entered on the app's `AsyncExitStack`, so the connection pool is released with the app — cleanly or on a failed startup. It raises rather than returning `[]` on an HTTP error, because the capability already isolates one failing query and a silent empty list would read as "the web knows nothing about this". Its other decisions — the page over the snippet, the depth, the per-document bound — are the `web_search` bullet above.
