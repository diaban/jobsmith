## What was decided, and why

- **0165 — a graph agent gets its own port**: the existing `JobService` speaks the DAG's request shape (query + document); a graph agent needed dicts (input, graph, label, `reply_to`, wait) instead, so it is a third half of `AgentService`, not a reshape of the other two. → docs/decisions/0165-graph-agent-served.md
- **0166 — a pushed ending is never delivered inline**: a slow or raising push must not delay or break the settlement; saved first, then a retried background task, keyed by `(job_id, attempt)`. → docs/decisions/0166-push-deliverers.md
- **0167 — a paused run gets its own status**: `needs_input` rather than folding the pause into an ending, because the told-by-attempt key (#170) has no room for two endings inside one attempt. → docs/decisions/0167-needs-input.md
- **0168 — a partial re-run is a new job, never a new attempt**: `attempt` counts tries at *one* request, and is also the key an ending is told by; a correction is a different request. → docs/decisions/0168-partial-rerun-is-a-new-job.md
- **0169 — Postgres CI needs a tried, not waited, advisory lock**: a waited `pg_advisory_lock` measured to hang forever against the migrations' `CREATE INDEX CONCURRENTLY`. → docs/decisions/0169-postgres-in-ci.md
- **0177 — amending is stop + checkpoint update + resume, split by who knows what**: the engine offers the mechanism (`amend_job`), the DAG gives it meaning (`drop_steps`); a step already running restarts, since LangGraph has no stop-at-boundary without the graph's cooperation. → docs/decisions/0177-amend-a-running-job.md
- **0187 — `retryable` is exactly the resume gate's own test**: `bool(pending)`, so the field and the gate can never disagree. → docs/decisions/0187-structured-failure.md
- **0189 — relaunch is opt-in, bounded, and claimed**: only the graph knows whether its nodes may safely run twice; without a claim, two managers on one store both relaunched (measured 2/2 failures). → docs/decisions/0189-orphan-relaunch.md
- **0191 — a transient failure is retried, replanning is left out**: capabilities already catch and emit failures rather than raising, so `RetryPolicy` never fires; a second planner call was judged to need a plan diff and a policy nothing has measured a need for yet. → docs/decisions/0191-repair-transient-steps.md
- **0194 — `Send` strips the append-only channels**: a sub-graph echoed `completed_capabilities`/`errors` back and the parent appended them again, so 0191's retry count was wrong before it shipped. → docs/decisions/0194-send-without-appended-channels.md
