## From “CLI + daemon (`cli/`) — where jobs actually run”

Embedded mode is honest about its limit: a job still *running* stops when the process exits (`recover_interrupted` settles it on the next start). What it already did is not part of that limit any more (#63): the records are the persistence's business and the default keeps them, so the embedded banner speaks only of running jobs and the persistence banner right after it says where records live (`[persistence: sqlite — jobs kept in <path>  (default; --db=memory keeps nothing)]`). `run`'s embedded note says the record is kept once the job ends.

## From “The composition root (`app/`)”

`agent.py`: `await build_app(agent=..., **overrides) -> AgentApp(manager, session_factory, agent_name, resources, registry, aclose)`. **`reports_dir` is resolved once, to an absolute path, before anything uses it** (`pick_reports_dir`: argument > `$JOBSMITH_REPORTS_DIR` > `<data dir>/reports`, #63) — every path a job records is built from it, and a record that outlives the process must not carry `artifacts/…` relative to wherever it was launched: from any other directory that is a path to nothing, which is exactly what a persistent job list would put on screen. It also declares what this deployment lets a capability **read** — `AgentContext(readable_roots=(reports_dir,))` (the resolved one), the tree the product's own paths point into, so a report a job wrote is a file the next request can name (#60). It also hands down the `PriorJobSource` a capability reads an earlier RUN through (#74) — one `StoreJobRepository` built here and given to both the manager and that port, because the registry is composed before the manager exists and two repositories over one store would be two answers to "what did that job produce". It composes ONE agent definition into a running product: providers, persistence, the agent's resources, registry, graph, JobManager, chat-session factory — all on one `AsyncExitStack`. The REPL and entrypoints live in `cli/`.

- **An unconfigured jobsmith keeps its jobs** (#63). The default was `memory`, so every surface built to find a job again — `jobs`, `job <id>`, `resume`, the TUI's list, the chat's announcement — was dead on arrival in the default configuration and looked broken rather than unconfigured. The default is now a SQLite file, and **SQLite is a core dependency, not an extra**: "a file when `.[sqlite]` happens to be installed, memory otherwise" would make one command behave differently on two machines, the silent difference refused everywhere else here (a capability nothing can serve stays out of the registry; a format nothing renders fails at startup). `langgraph-checkpoint-sqlite` is pure Python, so it costs no deployment constraint; `.[sqlite]` survives as an **empty** extra so existing install commands do not fail on an unknown one. `_open_sqlite` lost its `ImportError` guard with it — its absence is a broken install.

- **Where**: `data_dir()` — `$XDG_DATA_HOME/jobsmith` when that is set to an absolute path, **on every platform** (setting it is an explicit choice, and it is the one lever that relocates everything at once, which is how the test suite is fenced off); otherwise `~/.local/share/jobsmith` (Linux & co), `~/Library/Application Support/jobsmith` (macOS), `%LOCALAPPDATA%\jobsmith` (Windows) — stdlib only, three branches are not worth `platformdirs`. Never the working directory: a job list that depends on where the command was typed is the same surprise one level up. Reports live under it too (`reports/`, see `agent.py` below). The directory is created by the one thing that writes into it first (`_open_sqlite` makes the db file's parent, the Reporters and the artifact store make theirs), never by `data_dir()` itself. A relative `$XDG_DATA_HOME` is ignored, as the spec says.

- **`memory` stays a supported value, and must now be asked for by name.** Every test, `evals/harness.py` and the banking demo say `db="memory"` explicitly. `tests/conftest.py::sandboxed_data_dir` (session, autouse) points `$XDG_DATA_HOME` at a temp dir, clears `$JOBSMITH_DB`/`$JOBSMITH_REPORTS_DIR` (a developer's own must not become where a careless test writes), and **fails the run** if that directory exists at the end — a `build_app` that forgot `db="memory"` is caught by name instead of quietly adding jobs to the job list of whoever ran the suite. A test exercising the default on purpose points `$XDG_DATA_HOME` at its own `tmp_path`. The same fixture makes `load_dotenv` a no-op for the session (on `app/providers.py` and on every module already holding it by name): the entrypoints load `.env` with `setdefault`, so a test driving one on a machine whose `.env` names a `JOBSMITH_DB` would refill what was cleared and write outside the sandbox, unseen (`test_the_test_process_never_reads_a_dot_env`).

- **Every process of a user shares that file by default** — which is what makes it useful and what made #10 a prerequisite: `recover_interrupted` must not declare dead a job another live process is running. That is #10's subject and lives in `jobs/`, not here.

- **…and so every process writes to it, which SQLite only allows if each writer asks for the lock first.** Measured with five real processes on one file (`tests/test_sqlite_concurrency.py`, driving `tests/sqlite_hammer.py` straight on the LangGraph backends so no retry hides anything). Three findings, one per backend step:

  - **The store failed at once** ("database is locked", most processes, every run): each batch opens a *deferred* `BEGIN`, reads, then writes, and a read snapshot another process committed past cannot be upgraded — WAL's `SQLITE_BUSY_SNAPSHOT`, which never consults the busy timeout. The store's connection is therefore handed over wrapped in `_ImmediateBegin`, which turns the store's own `BEGIN` into `BEGIN IMMEDIATE`: the lock is taken before the first read, so a contended batch *waits* (the 5 s `connect(timeout=...)`) and reads a current snapshot. A wrapper on the connection, because the constructor argument is the one seam the store offers and "which BEGIN" is a property of the connection; nothing of LangGraph is subclassed or patched, and a private `_cursor` override would silently diverge on the next release. It depends only on the store saying `BEGIN`, which the two-process test pins. Cost, stated: the store's read batches queue behind another process's write too. **BEGIN now waits, and a statement already on aiosqlite's thread lands even if its awaiter is cancelled** — that is safe only because the store runs every batch in a background task of its own (`AsyncBatchedBaseStore`), so a cancelled `aput` stops waiting and never interrupts a batch between its BEGIN and COMMIT; `test_a_batch_cancelled_while_waiting_for_the_lock_leaves_no_transaction` pins it, and fails with "cannot start a transaction within a transaction" if a batch ever runs in the caller's task.

  - **Opening a fresh file together raced** — the store's migrations (read version, then apply, autocommitted, nothing held: "UNIQUE constraint failed: store_migrations.v", "duplicate column name") and, rarely, the WAL switch. Both go through `_while_another_process_sets_up`, a bounded retry on exactly those messages: every such failure is the other process having just done the same step, and the next attempt resumes after it. Serialising instead would need a lock `executescript` does not break (it commits any open transaction first).

  - **The saver never failed**, before or after — measured, not reasoned: its connection keeps sqlite3's implicit transactions, which open on the first INSERT, so it asks for the write lock before reading anything and the busy timeout applies. Its test stays so that remains measured.

  - `StoreJobRepository._io` used to retry "database is locked" (#10), which covered the first finding for job records only. With the store fixed where the connection is opened it had nothing left to catch short of a writer holding the lock past the busy timeout — measured: no "locked" error in 40 instrumented runs of #10's cross-process tests with the retry off — so it was **removed**, and a lock held past the timeout is now raised as the error it is. #10's cross-process tests are what prove the removal: 40/40 runs of `tests/test_cross_process.py` green without it.

  - **Measuring surfaced a race in the canceller, now fixed** (`JobManager._await_remote_stop`): it read the summary, then the control record, and an owner settling between the two reads (CANCELLED written, lease released) looked like an owner gone — a fence left behind and a second ending over the owner's. `BEGIN IMMEDIATE` made it frequent (reads now queue behind writes) but did not create it. The control record is read first now, which is sufficient because every path that gives a lease up writes its final summary BEFORE releasing (`_drive`'s normal end, cancel and failure; `_begin` hearing an early cancel), and a fenced owner releases nothing. `_settle` re-reads and never writes over an ending already written. The interleaving is forced, not waited for, in `test_an_owner_settling_between_the_canceller_s_two_reads_keeps_its_ending`.
