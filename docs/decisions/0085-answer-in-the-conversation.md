## From “Jobs layer (`jobs/`)”

**The report is a deliverable, not a trace**, and since #85 that is true of the *record* as well as of the step material: title + answer, then one line naming the run (`job_reference`). Everything else a document used to recite about itself — the request quoted in full, both timestamps, the session, the token bill, the plan table with its per-step cost column, the DAG — is **recorded, not recited**: `GET /jobs/{id}` and `jobsmith job <id>` serve it whole, and a reader who opened a file to read an answer was being handed the product talking about itself. Four decisions. **The way back stays, on every document and behind no flag** — a file nobody can trace to its run is the same class of defect as a deliverable nobody can find (#28), and it is the one thing the file cannot get from anywhere else. **`with_provenance` is the archive switch**, the same shape `with_annexes` already is (`FileReporter`, `make_reporter`, `compose_reporters`, and `build_document` sets `JobDocument.provenance` from it) and independent of it, because one is what the steps produced and the other is what the run was; neither is set in production wiring, both are there for a self-contained file. **The data is built either way and the flag only decides the rendering** — unlike `with_annexes`, which gates the *building* because that costs a `render_report` call into every capability that ran. **Nothing about the Reporters' architecture moved**: one `JobDocument`, three serializers, the PDF still the HTML page printed.

- **The evals contract changed with it, deliberately** — see the `evals/` section: `report_provenance` now scores the job id alone and `report_covers_plan` is gone, because the property it measured is no longer one the deliverable has.

## From “Chat layer (`chat/`)”

**A promoted run gets the same verbatim channel, and length is what decides where the answer is read** (#85). #83 gave the *synchronous* path a channel that nothing rewrites; a run that outlived the wait still handed its answer to the completion notice, which is an instruction to the chat model, which synthesises it — so for the promoted minority the file was the only place the words survived, which is precisely why the rest of #84 could not proceed (#96 then took it: see the `document_intent` sub-bullet). `JobNotificationMiddleware._deliver` writes it onto the **same** custom channel `launch_job` uses, so the reader sees a `Token` either way and the tool and the middleware stay strangers to the front-ends. Four decisions. **The threshold is length, not duration, and it is a deployment choice with an opinionated default**: `pick_inline_answer_max` / `$JOBSMITH_INLINE_ANSWER_MAX`, 2 000 characters (~300 words), in the style of `pick_sync_timeout` and `pick_db`. Two thousand because it is a **reading** budget and nothing else — roughly a screenful and a half of terminal, what a person reads where they are standing before they would rather open a document and keep it; a transcript is a place you scroll and a file is a place you keep. Deliberately not tuned to cost or elapsed time: a four-minute run can answer in two sentences. Unlike #83's duration it is known exactly at the moment the choice is taken, which is why this one needs no clock. `0` is supported and means "never", i.e. the behaviour this replaced. **Length only decides when there is something to decide between** — a run that wrote no file has nowhere else to put its text, so it is delivered whatever its length, including at `0`: that is a rule about losing text, not a policy about length, and it is what makes #84's remaining half safe to take. **The notice's wording is `chat/tools.py::_delivered`'s**, because a reader cannot tell whether a task ran in the turn or came back from the background and being told the same thing in two registers is how they would find out for no reason; `_notice_for` takes `delivered` and it changes exactly one thing — whether the model is asked to relay the answer or told to keep its hands off it. **The write happens before the model call it rides with**, so the answer arrives and then the sentence about it; a model call that then fails leaves the job unannounced and the answer shown, which is the same trade the notice already makes and the harmless half of it.

## From “Evaluating prompts (`evals/`)”

**The deliverable's contract changed, so two checks did** (#85). `report_provenance` asked for the job id **and** the request quoted back, and `report_covers_plan` for every executed step to be named: both encoded the *About this job* section, which a reader no longer opens. `report_provenance` now scores the one property that survived and could not be got anywhere else — the file names **which run wrote it** — and it is what fails, in both formats and on the deterministic tier, if the footer is ever dropped. `report_covers_plan` was **removed rather than inverted**: the honest inverse is "no step is named", and `research`, `analysis`, `documents` and `critique` are ordinary words a document about a subject uses legitimately, so a substring test on their absence would score the prose and not the machinery. What a plan did is the *record's* question, and `GET /jobs/{id}` is what answers it. Nothing else moved: the structural tier stayed 100%, and every remaining check still applies to at least one golden case.
