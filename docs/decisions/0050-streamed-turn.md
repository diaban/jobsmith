## From “The inbound port (`service.py`)”

**A turn is a flow, and the flow is the primitive** (#50). `stream(session_id, text)` / `stream_approval(session_id, approved)` are the abstract methods; `send`/`approve` are **concrete on the port itself**, defined as `terminal_of(self.stream(...))` — drain the events, return the one terminal. A turn is therefore driven in exactly one place, and a caller that waits and a caller that renders can never be told different things about the same turn. The events are dicts (`as_event`, built from the frozen dataclasses of `chat/runner.py`) for the same reason replies are: they cross HTTP, and a front-end deserializing a dataclass would be a third implementation. **`Message.content` is the turn's transcript, not the model's last message** — the concatenation of every `Token` yielded, in order (#83). It was the model's own message for as long as the tokens came from that message too, so the two were the same string and nothing said which one the invariant rested on. A tool that writes into the turn breaks the tie: the job's answer arrives as tokens and the model's reply is "at most one short sentence", so a terminal built from the model hands a caller that *waits* an answer with the result cut out of it — `POST /sessions/{id}/messages`, the surface a web UI will use (#8). Composing from the tokens leaves no second source of truth to drift. The one fallback is a model that streamed *nothing at all*, whose last message then stands in; it can never mask a missing job answer, because that answer is a token and any turn carrying one has a non-empty transcript. **The backing-parity suite is structurally blind to this class of defect** — it compares the two backings, which are the same code, so both are wrong together and it passes; `test_a_turn_answers_the_same_whether_it_is_waited_for_or_watched` is the one that drains a turn twice, once by `stream` and once by `send`, and compares the texts.

The two terminal dicts — `{"type": "message", "content"}` and `{"type": "proposal", "query", "rationale", "sources"}` — are byte-for-byte what `send` already returned (`sources`, the files a proposed job would open, joined them with #60: what the user approves has to be what they were shown, and it is a `list` rather than a tuple precisely so both backings answer with the same JSON).

**The overflow rule is the opposite of `/events`, and that asymmetry is the design.** A dropped progress tick is invisible and harmless — the next one supersedes it — so `subscribe` sheds under back-pressure on both backings. A dropped **token** is a lie: the sentence arrives shorter than the model wrote it and nothing in the text says so. So the chat stream never drops, and it is enforced structurally rather than by policy: there is **no queue anywhere on the path** — an async generator out of the runner, a `StreamingResponse` pulled by the server, `aiter_lines` yielded straight to the caller — so a slow reader slows the turn instead of losing part of it. What structure cannot decide, a refusal does: an undecodable SSE line raises `ChatStreamError` (where `_read_events` skips one and keeps listening), and a stream that ends without a terminal raises rather than answering with the last thing seen. `subscribe` needs its queue because a job runs whether anyone watches or not; a turn has exactly one reader, and it is waiting.

## From “CLI + daemon (`cli/`) — where jobs actually run”

**The REPL renders the flow, with no fallback branch** (#50, step 2). Both backings stream, so an "if it cannot stream, print it in one go" path would guard a case that cannot happen. The terminal event is deliberately *not* printed: the tokens already delivered it. A `ChatStreamError` mid-turn is caught, said out loud on stderr, and the loop continues — half a printed answer followed by silence is exactly the defect the no-drop rule exists to prevent, and the conversation itself lives in the checkpointer.

## From “Chat layer (`chat/`)”

**`chat/runner.py` is the twin of `jobs/runner.py`** (#50), and exists for the same rule: it is the ONLY module that knows what LangGraph's `astream` emits for a chat agent — the `("messages", (chunk, metadata))` pairs, the `("updates", {node: update})` ones, the `("custom", payload)` ones, the `model`/`tools` node names, `__interrupt__`. Without it that shape leaks through the service, through the API, and into every UI. Six frozen dataclasses come out: `Token(text)`, `ToolStarted(name)`/`ToolFinished(name)`, `JobStarted(job_id, query, rationale, sources, document_*, formats)`, and the two terminals `Message(content)`/`Proposal(query, rationale, sources)` — the duality `_reply` already carried, moved from a return value to the end of a flow. All three stream modes are needed and none is redundant: `messages` carries the answer as it is written, `updates` carries what a token cannot show (which tool was called, that the run stopped on an interrupt), and `custom` carries what a **tool** has to say while it is running. **Exactly one terminal is always yielded, last**, so a caller draining it for a reply never has to interpret an exhausted stream — `JobStarted` is deliberately not one: a turn that starts a job carries on.

- `ToolStarted` carries the tool's **real name** (`launch_job`), never a phrase. Turning it into prose a human reads is the presentation layer's business (`TOOL_ACTIVITY` in `cli/repl.py`), for the same reason `REPORT_MEDIA_TYPES` lives in `api/app.py` and not in `jobs/report.py`: the CLI and a future TUI word it differently, and neither wording belongs in the thing that reports the fact.

- **`awrap_model_call` still injects on a streamed turn** — probed before anything was built, because it is how a finished job reaches the conversation and a streaming path that skipped it would lose that silently (the turn still answers, it just never mentions the job). It holds because the tokens do not travel *through* the middleware: LangGraph's `messages` mode taps the model's own streaming callbacks, so `handler(request)` is untouched and the notices ride on `request.override(...)` exactly as before. `tests/test_chat_stream.py` pins it through `LocalAgentService.stream`, so a streaming path that built itself a middleware-less agent fails there and nowhere else.

## From “HTTP API (`api/`)”

**Chat**: `POST /sessions` → id; `POST /sessions/{id}/messages` returns `{"type": "message"}` or, where the gate was kept (`$JOBSMITH_APPROVE_JOBS`), `{"type": "proposal"}` (HITL interrupt surfaced over HTTP); client answers with `POST /sessions/{id}/approval {"approved": bool}`. A task runs inside the turn (#83), so a request here can last as long as the task — the adapter gained nothing for that, because a turn's duration was never its business. Both have a `/stream` twin (`.../messages/stream`, `.../approval/stream`) answering the same turn as SSE, event by event, ending on that same reply — additive, and what `DaemonClient` actually consumes (its `send` drains it). No queue behind them, unlike `/events`: the body is pulled from the turn itself, so a slow reader back-pressures through the socket into the model call and the answer stays whole. Unlike `/events` they *are* testable through `ASGITransport` — a turn's stream ends, so the buffering that hangs on an endless body is merely a delay here, and `tests/test_service.py` drives the event-by-event parity of both backings over it.
